## 2. Аудит протокола (основание решений)

Измерено на установленных Codex App Server **0.156.1** и Claude Agent SDK **0.3.278**.
Только `thread/list` и `thread/read`; **0 запросов модели**, ни одной мутации, SQLite и
rollout не изменялись. Сырые отчёты — `artifacts/subdialog-probe/report*.json`
(каталог в `.gitignore`).

- **`parentThreadId` в `thread/list` заполняется только при трёх условиях одновременно:**
  `sourceKinds` включает `subAgent*`, передан фильтр `cwd`, и **не** передан
  `useStateDbOnly: true`. На одном наборе: с `cwd` — 34/40 с родителем;
  с `useStateDbOnly:true` — **0/40**; без `cwd` — **0/40**. Один и тот же thread
  `01a12214-7b18…` без `cwd` отдаёт `null`, с `cwd` — `01a12214-250e…`.
  Поле заполняет разбор JSONL, а не state DB.
- **`forkedFromId` в `thread/list` не приходит никогда** (0 во всех пяти вариантах,
  включая известное ответвление). Есть только в `thread/read`.
- **`sessionId` всегда равен `id`** в обоих методах. Корень дерева сессий из rollout
  `session_meta.session_id` через протокол не отдаётся — как ключ группировки непригоден.
- **`source` — достоверный дискриминатор, доступный прямо в `thread/list`:**
  `{subAgent:{thread_spawn:{…}}}` исполнитель, `{subAgent:{other:"guardian"}}` служебное
  ревью, `"vscode"`/`"cli"`/`"appServer"` верхний уровень. Регистр ключей смешанный:
  внешний camelCase `subAgent`, внутренний snake_case `thread_spawn`.
- `sourceKinds: ['subAgent']` и `['subAgentOther']` вернули **идентичные множества**
  (135 == 135): фильтр источников исполнителей от служебных не отделяет.
- **Claude Code связей не сообщает вовсе.** `SDKSessionInfo` (`sdk.d.ts:5486`) — единственный
  тип, который возвращают `listSessions`/`getSessionInfo`, — не содержит ни родителя, ни
  источника ответвления, ни дерева сессий. `ForkSessionResult` отдаёт только новый
  `{ sessionId }`. Подагенты Claude своей сессии не получают.
- Перепись 379 локальных rollout: 247 guardian-ревью, 66 настоящих `thread_spawn`,
  1 пользовательское ответвление; у spawn-потомков `parent_thread_id == forked_from_id`;
  есть цепочки глубины 2.

## 3. Что реализовано

### Модель — `src/thread-relations.ts`

Чистая логика без IPC и React. `parentId` берётся **только** из `parentThreadId`, при его
отсутствии — из `forkedFromId`; заголовок, время, `cwd` и порядок в списке источником связи
не являются. `evidence` фиксирует доказавшее поле. `kind`: `root` / `spawn` / `service` /
`fork` / `unavailable`. `label` — `agentNickname`, иначе `agentRole`, иначе `agent_path`;
без значения backend подписи нет. `sessionId` не используется нигде.

`buildRelationGroups` группирует по **прямому** родителю: несколько планировщиков дают
несколько независимых групп, которые никогда не сливаются. Потомок без загруженного
родителя получает собственную группу «Родительский диалог не загружен» и не прикрепляется к
похожему родителю. Глубина больше одного поддерживается. Служебные потоки
(`guardian`/`review`/`compact`) складываются в отдельный список группы и показываются только
под свёрнутой строкой «Служебные диалоги агента: N».

### Host — `electron/thread-children.mjs`

Один read-only `thread/list` с `subAgent*`, обязательным `cwd` и без `useStateDbOnly`
(все три условия §2 закреплены тестом, который читает фактические параметры запроса).
`archived` не задаётся, поэтому архивный потомок не может вернуться этим путём.
Папка проверяется как и раньше: только точная зарегистрированная canonical папка.
Новая граница — `host:listThreadChildren`; allowlist мутаций **не** расширялся.

`electron/project-history.mjs` выделил общий `folderReader` (выбор read-only соединения,
проверка папки, перепроверка окна/сессии/клиента до и после запроса). Поведение и параметры
`listProjectThreads` не изменились — прежние 7 тестов проходят без правок.

### Интерфейс

- **Дерево проекта.** Строка родителя получает счётчик исполнителей и disclosure; потомки
  рисуются с отступом, направляющей линией, значком агента и подписью агента
  (`Franklin`, `Godel`). Группы свёрнуты по умолчанию; состояние хранится по
  `projectKey|parentId`, поэтому переключение вкладок его не сбрасывает.
- **Панель «Подагенты»** — переключатель рядом с «Архивом», панель поверх проектов.
  Карточки групп по всем папкам, счётчик «N подагента», отдельный фон у группы без
  родителя, строка «Связи недоступны: Claude Code не сообщает родителя диалога».
- Оба представления только навигационные. Меню ⋮ у потомков — **тот же** набор
  (`rename`/`archive`/`delete`/`fork`) с теми же блокировками `threadLocked`.

Снимки: `artifacts/subdialogs-tree.png`, `artifacts/subdialogs-panel.png` (просмотрены).

## 4. Границы: архив, поиск, пагинация, массовый выбор

- **Пагинация истории папки не изменена.** Составной курсор `desk:{cwd,codex,claude}`
  прежний. Потомки читаются отдельным вызовом со своим курсором, только когда папка
  раскрыта или открыта панель «Подагенты». Это сознательный отказ от подмешивания:
  страница из 40 записей заполнилась бы служебными потоками, а `nextCursor` папки перестал
  бы соответствовать видимому. Сценарий утверждает, что курсор связей никогда не попадает
  в запрос истории.
- **Архив** сохраняет прежнюю плоскую группировку: `listArchivedThreads` использует
  интерактивные `sourceKinds`, потомков в ней нет. Семантика `archive`/`delete` не
  менялась.
- **Поиск не изменён.** Потомки в результатах не появляются (интерактивные `sourceKinds`).
  Чип родителя в результатах **не добавлен** сознательно — см. §6, отличие 1.
- **Массовый выбор.** Названная область прежняя. Потомки не входят в `rows`, «Выбрать все»
  их не считает, в режиме выбора они инертны: без чекбокса, без меню и без перехода.
- Кнопка «Обновить диалоги» папки теперь перечитывает и историю, и связи. Ошибка чтения
  связей показывается отдельной строкой с «Повторить» и **не** затрагивает историю папки.
- Закрытие проекта очищает связи и раскрытые группы этой папки вместе с историей.
- Архив и «Подагенты» — взаимоисключающие наложения; открытие одного закрывает другое и
  сбрасывает режим выбора.

## 6. Отличия от утверждённого проекта

1. **Чип родителя в результатах поиска не добавлен.** Проект допускал его «если родитель
   известен». Измерение показало, что у интерактивных диалогов `parentThreadId` всегда пуст,
   поэтому элемент никогда бы не отобразился. Добавлять заведомо мёртвый UI хуже, чем не
   добавлять; поиск остался нетронутым.
2. **`electron/thread-children.mjs` не дублирует выбор соединения,** а использует
   выделенный из `project-history.mjs` общий `folderReader`. Иначе пришлось бы копировать
   ~40 строк проверок окна, сессии и папки. Контракт `listProjectThreads` не изменён.
3. **Кнопка «Обновить диалоги» папки теперь обновляет и связи.** В проекте этого не было;
   без этого у связей не оставалось способа обновиться из дерева.

## 7. Ограничения

1. **Claude Code связей не сообщает** — ни родителя, ни источника ответвления на уровне
   сессии. Любая группировка диалогов Claude была бы догадкой; показывается «Связи
   недоступны».
2. **`forkedFromId` в панели не показывается.** Требует `thread/read` на каждый диалог;
   отложено решением координатора. Модель поле уже учитывает (`kind: 'fork'`), поэтому
   добавление не потребует переделки.
3. **`parentThreadId` зависит от пути чтения.** Если Codex изменит scan-and-repair, связи
   опустеют. Интерфейс в этом случае просто не покажет групп — потомки не теряются молча,
   они остаются доступны в своей папке; но и предупреждения об изменившемся протоколе нет.
4. **Служебные потоки доминируют** (247/379 rollout, 135/141 связанных диалогов проекта) и
   отличаются только разбором `source`.
5. **Ручной способ создания исполнителей связей не даёт.** Диалоги, созданные как
   независимые верхнеуровневые threads (как агенты A/B/C/D этого поручения), останутся
   плоскими. Именно этим был мотивирован исходный отказ, снятый координатором.
6. **`E:\Extensions` не отдаётся `thread/list`** ни при одном фильтре, хотя все 66 локальных
   spawn-потомков лежат там. Причина не установлена — вероятно, папка не в state DB.
7. **Архивная панель вложенности не показывает** — там потомков нет по построению.
8. Длинные названия потомков в узкой панели обрезаются (полный текст в подсказке), как и у
   существующих плоских строк.
