# Автообновление Release: контракт двух дорожек

Задача: пользователь нажимает «Обновить» — приложение само скачивает установщик
из каталога портала, показывает прогресс, дожидается завершения работы агентов,
сохраняет рабочее место, закрывается, установщик молча ставит новую версию и
запускает её обратно. Портал, Jenkins и схему каталога НЕ трогаем.

Основание: [UPDATES.md](../UPDATES.md) (проверка и скачивание уже работают),
ночной механизм `electron/nightly-update.mjs` + `electron/update-checkpoint.mjs`
(ожидание занятости, снимок рабочего места, перезапуск) переиспользуется.

## Протокол запуска установщика — единственная точка стыка

Приложение запускает **скачанный и проверенный** установщик так:

```
"<staging>\Codex-Desk-Setup-X.Y.Z.exe" /S
```

Единственный аргумент — `/S`. Всё остальное передаётся **переменными
окружения** дочернего процесса:

| Переменная | Значение |
| --- | --- |
| `CODEX_DESK_UPDATE_PID` | десятичный PID работающего приложения |
| `CODEX_DESK_UPDATE_EXE` | полный путь к работающему exe |
| `CODEX_DESK_UPDATE_LOG` | полный путь к файлу отчёта |

ИСПРАВЛЕНО 2026-10-15 относительно первой редакции: параметры командной строки
вида `/UPDATEEXE="C:\путь с пробелом\x.exe"` ненадёжны — Node при spawn без
оболочки берёт в кавычки параметр целиком, и `${GetOptions}` разбирает такое
по-разному. Переменные окружения снимают вопрос кавычек полностью, и этот приём
в `installer.nsh` уже применяется (`CODEX_DESK_INSTALL_TARGET`).

Режим обновления включается наличием `CODEX_DESK_UPDATE_PID` вместе с
`${Silent}`. Без переменной тихая установка ведёт себя как прежде.

- Запуск detached, `windowsHide: false`, без оболочки. Сразу после успешного
  spawn приложение сохраняет снимок рабочего места и вызывает `app.quit()`.
- Сверка процесса идёт по полному пути (`CODEX_DESK_UPDATE_EXE`), а не по имени:
  Release и Nightly называются одинаково.
- В файл отчёта установщик пишет ОДНУ строку результата.

### Поведение установщика (дорожка B)

1. В тихом режиме с `CODEX_DESK_UPDATE_PID` существующая проверка «приложение
   запущено» не прерывает установку сразу, а **ждёт** завершения процесса: опрос
   по пути из `CODEX_DESK_UPDATE_EXE`, до **120 секунд**. Процесс НИКОГДА не
   завершается принудительно установщиком — это делает только само приложение.
2. Не дождался за 120 с → в файл отчёта строка `timeout`, выход БЕЗ установки.
3. Установился → строка `ok`, затем запуск
   `$INSTDIR\${APP_EXECUTABLE_FILENAME}` с аргументом `--updated` от имени
   текущего пользователя (как уже делает `DeskStartApp` на финальной странице).
4. Любая другая ошибка → строка `error`, ненулевой код выхода.
5. Правило «только для текущего пользователя» сохраняется: `/allusers` в этом
   режиме по-прежнему отвергается.

Коды выхода: `0` — установлено, `2` — отказ, `3` — не удалось выяснить, жив ли
процесс, прочее — сбой NSIS.

УТОЧНЕНО по итогам реализации B (принято дорожкой A, расхождений в коде нет):

- **Код 2 неоднозначен**: NSIS сам ставит errorlevel 2 при прерванной секции,
  поэтому сбой установки тоже приходит как `2`. Различать отказ и сбой следует
  **по строке отчёта**, а не по коду. Приложение код выхода и не читает: оно
  узнаёт итог по факту смены версии, а причину — из строки отчёта.
- `/allusers` в режиме обновления дополнительно пишет `error`, чтобы приложение
  не получило пустой файл.
- Отчёт пишется **до** запуска приложения: при неудаче `ExecShellAsUser` в файле
  останется `ok` — установка действительно прошла. Приложение обрабатывает
  случай «отчёт `ok`, а версия прежняя» отдельным текстом.

### Поведение приложения (дорожка A)

1. Скачивание потоком в `userData/updates/` с прогрессом (получено/всего),
   сверка размера и SHA-256 из карточки каталога — как сейчас, но не в «Загрузки».
2. Перед запуском установщика пишется `pending-update.json` в userData:
   версия, путь установщика, sha256, прежние версия и buildId, время, путь лога.
3. Ожидание занятых агентов, кнопка «Закончить процессы принудительно» и снимок
   рабочего места — по образцу `UpdateNotice.tsx` и `update-checkpoint.mjs`.
4. После перезапуска приложение читает маркер и лог:
   - версия изменилась → маркер и скачанный файл удаляются, показывается
     обычная страница «Что нового?»;
   - версия прежняя → маркер остаётся, показывается ошибка с кнопкой
     «Показать файл в папке» (запасной ручной путь никуда не девается).

## Границы

- Ничего не пушим: ни GitHub, ни Gerrit. Release не трогаем. Сборка — только
  Nightly и только по явному поручению владельца.
- Тексты интерфейса русские.
- Установщик не подписан сертификатом издателя. Проверка тихой установки на
  живой машине обязательна до слов «готово»; если Windows вмешается — это
  фиксируется как результат, а не обходится молча.

## Приёмка — задача считается доведённой, когда

1. `npm.cmd run check` зелёный (типы, сборка, полный набор тестов).
2. Новые unit-тесты обеих дорожек проходят.
3. Собран Nightly, и на нём проверен полный путь: прогресс → ожидание занятой
   вкладки → принудительное завершение → тихая установка → перезапуск с теми же
   вкладками.
4. Проверен отказной путь: приложение не закрылось → `timeout`, установки нет,
   приложение продолжает работать.
5. `docs/UPDATES.md` и `docs/RELEASES.md` описывают новое поведение.
6. Отчёт владельцу: что проверено живьём, что фикстурами, что осталось риском.

Уточнения, которых в контракте не было:

1. **Код 2 неоднозначен.** NSIS при прерванной секции сам ставит errorlevel 2,

3. Отчёт пишется **до** запуска приложения. Если `ExecShellAsUser` не сработает,
   в файле всё равно будет `ok`: установка-то прошла, и ручной запуск её
   завершает. Файл перезаписывается целиком (`FileOpen ... w`).

2 с, бюджет 120 000 мс по `GetTickCount`, затем `Sleep 1500` на освобождение
файлов. Принудительного завершения нет нигде. Ветка ожидания собрана под

старый деинсталлятор, и тот унаследовал бы те же переменные — его поведение
оставлено прежним.
