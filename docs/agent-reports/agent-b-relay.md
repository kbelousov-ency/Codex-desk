Сделано:

- Relay хранит четыре пользовательские настройки уведомлений в SQLite
  (`turnCompleted`, `actionRequired`, `commandFailed`, `presence`); новые пользователи
  получают все четыре включёнными. Добавлены `GET/PUT /api/notifications` с ACL по

  ответа, путь и причина не попадают в Bot API.

  чистятся вместе с 30-дневным audit. При `429` relay уважает `retry_after` и
  повторяет отправку после указанной задержки. Состояние команд и encrypted payload
  прежнего replay-пути не изменено.
- `start-live.ps1` печатает чистый `wss://host` для поля «Адрес сервера» с пометкой,

## Подготовка первого живого прогона — owner launcher

Добавлены [`relay-server/start-live.cmd`](../../relay-server/start-live.cmd) для
двойного щелчка и [`relay-server/scripts/start-live.ps1`](../../relay-server/scripts/start-live.ps1).
Скрипт собирает production Mini App с `VITE_LOCAL_RELAY=0`,
`VITE_TELEGRAM_FIXTURE=0`, `VITE_RELAY_URL=/api`, выбирает `cloudflared` раньше
`ngrok`, а при отсутствии обоих использует официальный пакет
`Cloudflare.cloudflared` через winget либо официальный Windows amd64-релиз
Cloudflare с GitHub. Сторонние зеркала не используются.

Туннель запускается до relay, origin извлекается из его stdout/stderr в памяти,
затем relay получает только process-local environment: production guard,
allowed origin туннеля, static directory, AppData SQLite и постоянный AES-ключ.
Ключ создаётся один раз и хранится DPAPI-защищённым файлом в
`%LOCALAPPDATA%\KuzmichRelay`; token BotFather вводится через `Read-Host
-AsSecureString` и не попадает в аргументы, файлы, логи или родительский env.
После health-check печатаются три строки для владельца: ссылка BotFather,
`wss://<origin>/bridge/v2` для Кузьмича и напоминание не закрывать окно.
Ctrl+C завершает relay и tunnel через дерево процессов.

Есть bounded `-SyntheticTest` с фиксированными synthetic credentials — он не
обращается к Telegram и не принимает настоящий token. Фактический результат
прогона и возможность сети записаны ниже после запуска.

Приёмочная доработка launcher: окно HTTPS-origin в SyntheticTest теперь 300 секунд,
каждая попытка использует `Invoke-WebRequest` и fallback `curl.exe`, проверяет
`id="root"`, примерно раз в минуту вызывает `ipconfig /flushdns`. При исчерпании
окна выводятся origin, точное последнее исключение и последние строки stdout/stderr
relay и tunnel из `Reader` через `Read-Queue`. В owner-режиме после трёх строк запуска
проверка работает в основном цикле без остановки relay: печатает «Ссылка проверена,
открывается» либо DNS-предупреждение через пять минут.

## Доработка приёмки этапа 3 — транспортный replay

Уточнение владельца разделяет два разных повтора: повторный POST телефона
возвращает прежнюю команду без dispatch, а reconnect bridge требует повторной
доставки ранее принятой незавершённой команды. Прежний запрет transport replay
ниже сохранён как история и больше не действует.

- После `welcome` и первого **применённого свежего полного snapshot** relay
  повторно доставляет незавершённые команды этой установки с прежними
  `commandId`, `userRef`, действием, текстом и `expectedTurnId`. На одном
  соединении каждая команда доставляется повторно не больше одного раза;
  последующие snapshot/resync не запускают новый цикл.
- Терминальные статусы — только `executed` и `rejected`, при любом outcome.
  `null/queued/accepted/uncertain` участвуют в сверке. Relay не выдумывает статус:
  его меняют только `command_result`/`command_updated` bridge. Именно журнал
  bridge и `getOperation` предотвращают второе исполнение.
- Повторы дозируются; перед каждым кадром заново проверяются статус команды,
  владелец установки и действующее соединение. Разрыв/замена соединения отменяет
  старую доставку. Новые запросы к офлайн-установке по-прежнему отклоняются сразу.
  Исчезнувшая из snapshot вкладка не оставляет прежнюю команду висеть навсегда:
  исходный запрос доставляется bridge для свежей проверки и `unknown_tab`.
  Новые команды и выдача читающих payload проверяют актуальные права вкладки.

### Хранение и перезапуск

Для восстановления после перезапуска relay исходный запрос до терминального
статуса хранится в SQLite **зашифрованным AES-256-GCM**. Запись исходного запроса
и ключа идемпотентности выполняется до первого dispatch. AAD связывает ciphertext
с владельцем, установкой, ID команды, исходным `userRef` и fingerprint; nonce
случайный для каждой записи. Расшифрованный запрос заново валидируется и сверяется
с неизменяемым fingerprint. Открытый текст, ответы читающих действий и свободный
`detail.message` в SQLite/WAL и audit не попадают.

Для файловой БД нужен `RELAY_COMMAND_PAYLOAD_KEY`: канонический base64url-ключ
из 32 случайных байт, передаваемый через environment и сохраняемый между
перезапусками. В БД хранится только отпечаток ключа; другой ключ отвергается,
чтобы не смешивать зашифрованные записи. Это серверный ключ хранения, не
credential устройства: приватные Ed25519-ключи по-прежнему остаются на ПК.
Локальные in-memory фикстуры автоматически используют временный ключ.
Подробности запуска и ограничения — [README](../../relay-server/README.md).

При `executed`/`rejected` и отвязке установки поля ciphertext/nonce/tag очищаются
в действующей записи. Это логическое удаление: прежние зашифрованные страницы
могут оставаться в WAL/backup и расшифровываться при наличии серверного ключа.
Гарантии физического стирания истории SQLite здесь нет. Ответы `get_state` и
`get_last_answer` не сохраняются даже зашифрованными и не восстанавливаются
старому HTTP-запросу после обрыва.

У старых fingerprint-only записей `send/stop` исходного текста/хода не существует,
поэтому восстановить его миграцией невозможно. `replayUnavailable` сообщает
`legacy_payload_missing`, сохраняя wire-статус; Mini App показывает проверку на ПК.
Точный повтор исходного POST может восстановить зашифрованный запрос после
совпадения fingerprint, но **не отправляет** его заново: доставка возможна при
следующем reconnect. Для старых читающих запросов исходный конверт восстанавливается
из полей и проверяется по fingerprint. Повреждение ciphertext также даёт отдельную
диагностику, без подмены статуса или нового ID.

**Правило TTL утверждено владельцем:** ключи идемпотентности живут не меньше
установки, в v1 TTL нет. Fingerprint/ID/status сохраняются и после отвязки;
30-дневная очистка audit их не затрагивает. Правило зафиксировано в
[API.md](../../relay-server/API.md). Прежний вопрос о TTL закрыт.

### Backend и приватность

- `POST /api/installations/:id/commands` принимает клиентский `commandId` и
  разрешённый payload. `GET /api/installations/:id/commands/:commandId` возвращает
  только текущую запись команды. Точная схема — [API.md](../../relay-server/API.md).
- Неизменяемый отпечаток `tabId/action/text/expectedTurnId` записывается **до**
  отправки. Повтор того же ID и тела возвращает существующую команду без нового
  WS dispatch; другое тело — HTTP 409. После перезапуска правило сохраняется.
  Нет фонового повторного исполнения или серверной очереди.
- Новая команда требует текущего аутентифицированного OPEN-соединения bridge
  версии не ниже 2.2 и полного snapshot. Presence grace не считается готовностью
  доставить команду. Офлайн/нет snapshot — 409 `not_connected`, без записи новой
  команды; bridge 2.1 остаётся доступен для чтения, команды требуют обновления.
- Статусы **дословно wire**: `queued/accepted/executed/uncertain/rejected` +
  `outcome`. До первого подтверждения статус `null`, это квитанция отправки,
  а не выдуманный `queued`. `sent/delivery_unknown` описывают только транспорт.
  Ни timeout, ни reconnect, ни отзыв не меняют wire-статус. Поздний ACK после
  `uncertain` принимается только от bridge; старый GET не откатывает итоговый UI.
- SQLite v4 использует `command_ledger`; прежняя четырёхстатусная таблица
  сохранена отдельно как `legacy_commands_v3`, без переписывания исторических
  строк и без участия в обработке новых команд.
- **Текст команды вообще не записывается в SQLite/WAL** — это строже, чем удалять
  его после терминального статуса. Для конфликта ID хватает отпечатка, а без
  очереди нет причины хранить текст. `expectedTurnId`, читающий payload и свободный
  `detail.message` также не записываются. Audit содержит event/IDs/time;
  безопасный `detail.code` переводит клиент.
- Читающий POST ожидает до 10 секунд. Payload достаётся только исходному HTTP-
  запросу после повторной проверки session/owner/tab/живого bridge. Нет payload
  в GET, дубликате POST, WS, resync или SQLite. После timeout/abort/отзыва waiter
  удаляется; статус команды при этом не подменяется. Поздний ответ не кэшируется.
- ACL проверяется на установке и вкладке. Лимит — 30 новых команд/мин на
  пользователя, одновременно до 5 ожидающих чтений. Максимум текста — 32 000
  единиц UTF-16; переносы сохраняются. Тело команд ограничено 256 КиБ.
  Slash-команды и поля `cwd/model/access/attachments` не проходят API.

### Mini App

- Карточка вкладки содержит поле текста и четыре предусмотренных действия.
  Новых вкладок, терминала и истории переписки нет. Занятость, офлайн, отказ,
  ошибка исполнения и `uncertain` показываются отдельно.
- «Остановить» сначала вызывает **новый** `get_state`. Подтверждение показывает
  конкретный `activeTurnId` и разрешается только при `actions.stop: true`.
  `stop.expectedTurnId` остаётся тем, который видел пользователь. При `stale_turn`
  нет автоматического выбора нового хода: нужно заново запросить состояние
  и явно подтвердить его остановку.
- Статусы приходят по WS, с безопасным GET fallback для `null/queued/accepted`.
  При `uncertain` показано «Требуется проверка на компьютере» и только проверка
  того же ID; кнопки повторного выполнения нет. Потеря HTTP-ответа сохраняет
  исходный ID. Защита от двойного клика работает до React-render.
- «Последний ответ» — отдельный запрос. `{answer:null}` означает, что ответа
  ещё нет. Текст показывается как plain text, без HTML, открытия ссылок или чтения
  файлов. Контролы не используют payload неуспешной команды.
- Отключение, отзыв, смена вкладки, потеря авторизации и unmount отменяют ожидающие
  чтения и очищают содержимое. Поздний Promise не возвращает старый ответ или
  подтверждение остановки в интерфейс.

поздний ACK, гонку `command_updated` перед `command_result`, timeout/abort,
проверку raw SQLite/WAL (UTF-8/UTF-16) на отсутствие текста и payload.

18 новых DOM-проверок защищают `status:null` polling, один POST при двойном клике,

точный ход остановки, расхождение часов и запоздалый GET после WS-результата.

Браузерный e2e проверяет реальный локальный relay: отправку с
`queued → accepted → executed`, дубликат/конфликт, `uncertain` и безопасную проверку

остановку, офлайн-отказ и отзыв во время queued-команды. Итог: **0 внешних HTTP/WS,
0 ошибок JavaScript, 0 неожиданных HTTP-ошибок**, отдельно проверен ожидаемый

### Вопросы и различия для владельца / Агента А

1. В 2.2 осталось разрешение повторной доставки relay после обрыва. Последнее
   поручение владельца B строже: **тот же commandId не отправляется в bridge
   второй раз**. Реализовано именно поручение владельца; автоматического replay нет.

3. В JSON-примере `hello.proof` по-прежнему подписан как `<base64url HMAC>`

## Вопрос к Агенту А через владельца — блокирует production hello

Контракт требует `proof = HMAC-SHA256(raw(deviceSecret), challenge-message)`.
Поручение Агенту B требует хранить на сервере **только хэш** device credential.
Из `SHA-256(deviceSecret)` невозможно вычислить такой HMAC для нового challenge.
Поэтому после перезапуска сервер с корректным hash-only хранилищем не сможет
проверить `hello`. Хэш нельзя незаметно подставить вместо ключа — это изменит wire
семантику и не совпадёт с bridge.

Нужно решение владельца/Агента А: либо проверяемая по хэшу/публичному ключу схема
аутентификации в контракте, либо явное разрешение восстанавливаемого хранения
секрета. Derivation от master key в env формально оставляет в SQLite лишь хэш,
но позволяет серверу восстановить каждый deviceSecret; это **не** принимается
за разрешённый обход требования без решения владельца.

До решения production verifier должен отказывать безопасно. Fixture verifier
может держать тестовые секреты только в памяти для проверки остальных wire-фреймов;
такой прогон не доказывает готовность production authentication. В обновлённом
контракте `pair_confirm` передаёт `nonce` и `claimantUserId`: проверяются хэш nonce
и точное совпадение claimant. В SQLite остаётся только nonceHash; при restart
незавершённая pairing-сессия начинается заново.

Реализованы два самостоятельных пакета. Локальная цепочка Mini App → HTTP/WS API →
relay → подставной bridge работает; production-привязка намеренно заблокирована
противоречием контракта выше. Это **не** завершённая production-интеграция.

## Локальный запуск

Полные инструкции, HTTPS-туннель cloudflared/ngrok и отдельный тестовый бот
BotFather — [relay-server/README.md](../../relay-server/README.md).
Короткий путь без Telegram, в двух терминалах из корня проекта:

```powershell
cd relay-server
npm.cmd ci
npm.cmd run fixture
```

```powershell
cd miniapp
npm.cmd ci
$env:VITE_LOCAL_RELAY = '1'
npm.cmd run dev -- --host 127.0.0.1
```

Mini App: `http://127.0.0.1:5173`. Для отдельной UI-фикстуры без relay удалить
`VITE_LOCAL_RELAY` из environment и открыть `http://127.0.0.1:5173/?fixture=1`.
Ни bot token, ни настоящий Telegram для этих режимов не нужны.

## Дополнительные вопросы к Агенту А через владельца

1. Основной блокер HMAC/hash-only описан выше; контракт не изменялся.
2. `TabSummary` wire содержит семь полей, поручение B — пять хранимых. Сейчас два
   дополнительных поля отбрасываются; для отдельной активности каждой вкладки
   потребуется явное согласование расширения API/хранения.
3. Для этапа 3 надо согласовать отображение wire `queued/rejected` и
   `executed + outcome=failed` в серверные `accepted/executed/failed/uncertain`.
   Сейчас команды не принимаются и неоднозначное отображение не используется.
4. Раздел «Порядок» сохраняет epoch при reconnect и требует продолжать revision,
   но инвариант № 4 требует строго большего epoch после каждого reconnect.
   Relay следует правилу порядка: принимает полный snapshot с той же epoch
   и большей revision. Просьба согласовать формулировку инварианта.

## Этап 5 — чистка и закрепление (2026-10-15)

Изменения ограничены `relay-server/`, `miniapp/` и этим добавленным разделом.
Исторические разделы отчёта, включая прежний переходный wrapper, сохранены без правок.

Сделано:

- В `relay-server/src/bridge.ts` удалён compatibility bridge `event.payload`.
  Поля notice читаются только непосредственно из `event` по контракту 2.3.
  Wrapper игнорируется без пуша и разрыва WebSocket; порядковая revision учитывается,
  как для неизвестного noticeKind, чтобы следующий корректный event не создавал gap.
- Добавлен реальный WebSocket regression-тест: wrapped notice не вызывает Bot API,
  соединение остаётся открытым, следующий нормативный notice с теми же полями успешно
  отправляется. Тесты уведомлений/dedup переведены на прямые поля, включая `turnId: null`.
- В Mini App для `running`/`blocked` рядом с отключённой отправкой показано:
  «Беседа занята. Отправка станет доступна, когда задача закончится.»
  Кнопка связана с пояснением через `aria-describedby`. Два DOM-теста проверяют
  подсказку, отсутствие отправки при клике и её исчезновение/доступность кнопки
  после возврата в `idle`. Протокол и доступные действия не расширялись.
- Сверены и дополнены `relay-server/API.md`, `relay-server/README.md`, `miniapp/README.md`:
  дословные `queued/accepted/executed/uncertain/rejected` плюс outcome; отсутствие
  отдельного статуса failed; четыре настройки уведомлений и их источники; presence,
  dedup и 429; единственный прямой формат notice; Ed25519 устройства отдельно от HMAC
  Telegram initData. Исторические причины миграции и инертный legacy HMAC сохранены.
  Уточнено, что исходный текст в БД не хранится **в открытом виде**: нетерминальное
  encrypted body необходимо для согласованного replay, терминальный статус удаляет его.
