## 2. Формат хранения

`electron/thread-groups.mjs`, `ThreadGroupStore` → `thread-groups.json` в userData канала
(рядом с `claude-archive.json`, тем же способом записи).

```json
{
  "version": 1,
  "groups": [
    {
      "id": "g-5f1c0e2a-8b44-4a90-9c31-0d2e7a6b1f33",
      "name": "Переезд на роутер",
      "cwd": "E:\\My projects\\CodexDesk",
      "rootThreadId": "01a12214-250e-7873-87c7-81c9c121b8be",
      "createdAt": "2026-10-09T12:00:00.000Z",
      "updatedAt": "2026-10-09T12:04:11.512Z",
      "members": [
        { "threadId": "01a12214-250e-7873-87c7-81c9c121b8be", "addedAt": "2026-10-09T12:00:00.000Z" },
        { "threadId": "claude:11111111-2222-3333-4444-555555555555", "addedAt": "2026-10-09T12:04:11.512Z" }
      ]
    }
  ]
}
```

- **Стабильный локальный ID** `g-<uuid>`; имя переименовывается, ID не меняется.
- **Группа принадлежит одной рабочей папке** — так же, как думает боковая панель.
- **Один диалог состоит максимум в одной группе**, поэтому «убрать из группы» однозначно.
  `assign` в другую группу переносит, а не дублирует.
- `rootThreadId` — необязательный главный диалог (планировщик). Корень всегда входит и в
  `members`, поэтому порядок строк предсказуем: корень первым.
- Идентификатор диалога — UUID Codex или `claude:UUID`; строка сохраняется как есть, чтобы
  совпадать с тем, что уже пришло в renderer из истории.

Проверки и границы: имя 1…100 символов в одной строке без управляющих символов, `cwd` —
абсолютный путь, максимум 200 групп, 500 участников в группе, 4 МиБ на файл.
Запись атомарная (`wx` + уникальный временный файл + `rename`, режим 0600), операции
сериализованы одной очередью. Повреждённый файл или чужая версия схемы **не перезаписываются
и не считаются пустыми**: операция сообщает об ошибке с именем файла, чтобы его можно было
восстановить. Отсутствующий файл — нормальное «групп пока нет».

Файл **отделён** от нативных данных: транскрипты CLI, SQLite, история Claude и
`config.toml` Codex не читаются и не изменяются этим кодом. Сами агенты о группах не знают.

## 3. Миграция существующих диалогов

Миграции данных нет и не требуется: группы — новая сущность, прежних записей не существует.

- Все уже существующие диалоги обоих агентов **остаются там же** и попадают в «Без группы»,
  пока пользователь явно не добавит их в группу. Ничего не назначается автоматически.
- Диалоги, созданные вне приложения (терминальный Codex/Claude, VS Code, другая машина),
  появляются в истории папки как раньше и тоже попадают в «Без группы».
- **Пока в папке нет ни одной группы, боковая панель выглядит ровно как прежде**: одна
  секция «Без группы» рендерится без заголовка, плоским списком в прежнем порядке
  (`onlyUngrouped`). Заголовки секций появляются только после создания первой группы.
- Удаление диалога снимает его из всех групп (`ThreadGroupStore.forget`, вызывается из
  `host:manageThread` после успешного `delete`). Сбой этой уборки **не отменяет** удаление:
  группировка — только представление.
- Закрытие проекта убирает его группы и свёрнутые секции из состояния renderer; файл при
  этом не трогается, и повторное добавление папки возвращает прежние группы.
- Архивация диалога группу не меняет: диалог уходит из истории папки, запись о членстве
  остаётся и считается в «не на загруженных страницах». После восстановления он снова
  виден в своей группе.

## 4. Действия и их расположение

| Действие | Где |
| --- | --- |
| Создать группу | ⋮ папки → «Новая группа диалогов…»; ⋮ диалога → «В новую группу…» (диалог становится главным); панель «Группы» → кнопка у названия папки |
| Добавить существующий диалог | ⋮ диалога → «В группу «…»» (до 8 групп в списке) |
| Убрать диалог из группы | ⋮ диалога → «Убрать из группы» (видно только если диалог в группе) |
| Переименовать группу | ⋮ группы в заголовке секции → «Переименовать группу…» |
| Удалить группу | ⋮ группы → «Удалить группу…» |
| Новый диалог сразу в группе | `+` в заголовке секции группы |
| Свернуть/развернуть группу | заголовок секции |
| Обзор всех групп | нижний переключатель «Группы» (там, где раньше «Подагенты») |

Окно создания/переименования прямо говорит: «Группа — это организация диалогов в Кузьмиче.
Она хранится только в приложении и не меняет историю, настройки и память агентов.»
Окно удаления: «Сами диалоги, их история, вкладки и черновики останутся — они просто
вернутся в «Без группы».» Удаляется только группировка; `manageThread` при этом не вызывается.

Новый диалог, начатый из заголовка группы, вступает в неё **когда у него появится ID** —
то есть после первой отправки (до этого у вкладки нет диалога). Сценарий проверяет оба
момента: до отправки назначения нет, после — ровно одно и именно для созданного диалога.

## 5. Поведение для Codex и Claude

- **Группы работают одинаково для обоих агентов.** В одну группу можно положить диалоги
  Codex и Claude вместе — проверено и модульно, и в сценарии.
- **Нативные связи Codex сохранены.** Где backend сообщает `parentThreadId`, потомки
  по-прежнему вложены под родительской строкой, с подписью агента (`agentNickname`) и
  свёрнутым счётчиком служебных guardian-потоков. Измеренные условия чтения не изменились
  (`subAgent*` + фильтр `cwd` + без `useStateDbOnly`), см. [agent-c-subdialogs.md](agent-c-subdialogs.md).
- **Приоритет у пользователя.** Если зависимый диалог явно добавлен в группу, он становится
  обычной строкой этой группы и больше не вкладывается под нативного родителя — один диалог
  всегда ровно в одном месте.
- **Claude.** Нативного родителя SDK не сообщает (`SDKSessionInfo` не имеет такого поля), и
  это больше нигде не выводится как ограничение: диалог Claude просто лежит в «Без группы»,
  пока его не сгруппируют. Формулировка «Связи недоступны» удалена из интерфейса и кода.
- Никаких утверждений о нативном родстве группировка не создаёт: имя группы задаёт
  пользователь, членство — явное, и ничего не выводится из заголовков, времени или порядка.

## 6. Сохранённое поведение

- **Пагинация.** История папки и чтение зависимых диалогов не изменены, курсоры прежние.
  Группы читаются отдельным вызовом без курсора. Участники, которых ещё нет на загруженных
  страницах, показываются числом («5+», «Ещё N: не на загруженных страницах»), а не угадываются.
- **Поиск** не группируется и не изменён: результаты остаются плоским списком по папкам.
- **Архив** не группируется; панель архива прежняя.
- **Массовый выбор** сохраняет прежнюю названную область «загруженная история одной папки»:
  в `rows` входят те же диалоги, меняется только порядок их показа по секциям.
- **Переименование, ответвление, архивация, удаление, вкладки** — прежние пункты ⋮ и прежние
  блокировки `threadLocked`; пункты групп добавлены отдельным блоком под разделителем.

## 8. Ограничения

1. **Группы видны только в Кузьмиче.** В терминальном `codex`/`claude --resume` диалог
   остаётся обычным: оболочка сознательно не пишет в данные агентов. То же ограничение, что
   у локального архива Claude.
2. **Группы не синхронизируются** между Release/Nightly/Experimental: у каналов отдельные
   профили userData, а значит и отдельные `thread-groups.json`.
3. **Участники вне загруженных страниц показаны числом**, а не именами: имя диалога
   приходит только из истории, и выдумывать его нельзя. Нажать «Загрузить ещё» — и они
   появятся.
4. **Группа привязана к папке.** Диалог из другой рабочей папки в неё не добавить; для
   второй папки нужна своя группа.
5. **Поиск и архив не сгруппированы** — сознательно, чтобы не менять их область и пагинацию.
6. **Новый диалог вступает в группу только после первой отправки**, потому что до этого у
   вкладки нет идентификатора диалога. Если вкладку закрыть раньше, назначения не будет.
7. **Автоматической очистки «мёртвых» участников нет**, кроме удаления диалога через
   приложение. Диалог, удалённый в самом CLI, останется записью в группе и будет
   отображаться как «не на загруженных страницах».
8. **Нет Electron/preload/IPC-сценария** для новых каналов: `host:listThreadGroups` и
   `host:manageThreadGroup` покрыты модульными тестами хранилища и сценарием renderer с
   подставным мостом, но не packaged-прогоном.
9. Длинные названия групп и диалогов в узкой панели обрезаются (полный текст в подсказке).
