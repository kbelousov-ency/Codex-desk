# Codex и Claude Code через CLI — 2026-09-19

Пользователь попросил переключать агента с Codex на Claude и подтвердил использование **Claude Code CLI**. Это отдельный движок, не модель Codex и не замена App Server прямыми вызовами API.

## Использование

В нижней строке composer появился выбор «Агент»: Codex / Claude Code. Смена открывает **новую вкладку** в той же папке. Старая беседа, черновик, очередь, выбранная модель и процесс остаются у прежнего агента. Истории не переводятся и не пересылаются другому агенту скрытым сообщением. Вкладки и строки истории отмечены значком агента (`src/AgentLogo.tsx`: стилизованный шестизвенный узел для GPT/Codex и восьмилучевая звезда для Claude, монохромные inline-SVG, не фирменные файлы логотипов); прежняя текстовая метка «Claude» в дереве и суффикс «· Claude» во вкладке убраны 2026-09-19 по замечанию пользователя. Значки декоративные (`aria-hidden`), чтобы не менять доступные имена кнопок в сценариях. Ответы/пояснения/разрешения подписаны правильным именем.

Требуется установленный Claude Code. Поиск native claude.exe — `%USERPROFILE%/.local/bin` и PATH; при отсутствии можно выбрать exe в настройках текущей вкладки. Вход доступен из настроек — см. ниже. Используются его существующие auth/env/settings/CLAUDE.md/MCP/инструменты. Приложение не добавляет system prompt, не включает bare/safe-mode/strict-mcp и не пишет Claude config; авторизационные данные сохраняет сам штатный CLI при явном входе пользователя.

Модели и effort берутся из stream initialize и get_settings; текущее **точное** имя сохраняется, даже если оно не совпало с alias каталога (нельзя автоматически заменить `claude-fable-5-1` на `[1m]`). На этом компьютере фактически получены `gpt-6-astra / ultra` и `claude-fable-5-1 / medium`; это наблюдение, не hardcoded defaults.

## Вход через браузер и сбой OAuth — 2026-09-21

Во вкладке Claude откройте **Настройки → Авторизация Claude Code → Войти через браузер**. Открывается видимый терминал установленного CLI с `auth login --claudeai`; CLI запускает web-авторизацию и сохраняет её обычным способом. Этот вход используется и в терминальном Claude с тем же окружением. Кнопка **«Проверить вход»** получает свежий `claude auth status`, отдельно от stream initialize. Настройки входа доступны также при неудачном подключении и без созданного диалога. В PowerShell эквивалент: `& "$env:USERPROFILE\.local\bin\claude.exe" auth login --claudeai` (для стандартного расположения native CLI).

`electron/claude-auth.mjs` координирует один вход на экземпляр приложения. Занятые Claude-вкладки, подтверждения и открытые терминалы блокируют начало; простаивающие Claude-процессы завершаются с ожиданием фактического выхода через `stopAndWait` перед запуском login. Новые операции Claude до закрытия окна авторизации ждут; вкладки Codex продолжают работать. Затем вкладки Claude заново подключаются и возобновляют прежний диалог с моделью/effort/доступом вкладки; черновик остаётся, очередь приостанавливается и сама не отправляется. Успешное закрытие терминала само по себе не означает успешного входа: результат проверяется отдельным `auth status`. Внешние терминалы и другие экземпляры Release/Nightly этот локальный координатор не останавливает.

Команды используют выбранный во вкладке exe, её cwd и обычное окружение, включая `CLAUDE_CONFIG_DIR`. PowerShell запускается без профиля; аргументы передаются безопасными литералами. Host принимает только публичные поля статуса (`loggedIn`, `authMethod`, `email`, `subscriptionType`, `apiProvider`), добавляет `configDirectory`/`loginInProgress`; код 1 со штатным `loggedIn:false` — нормальный ответ, остальные сбои показываются без сырого stdout/stderr. Секреты, OAuth URL и auth-коды не проходят через renderer/журналы. Файлы credentials оболочка не читает и не переписывает. При выходе из приложения начатый интерактивный login не уничтожается.

Причина обращения пользователя: вход повторно пропал, а запустить его из интерфейса было нельзя. Проверено на этом компьютере:

На уровнях процесса/User/Machine отсутствовали проверенные `CLAUDE_CONFIG_DIR`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY` и переключатели сторонних провайдеров.
- В нативном транскрипте `C:\Users\LEGION-PC\.claude\projects\E--My-projects-CodexDesk\27793cf9-9196-4381-b3e8-71394e933d38.jsonl` есть `authentication_failed`: `2026-09-20T07:48:23.864Z`, `07:50:40.813Z`, `17:07:19.329Z`; текст: **`Failed to authenticate: OAuth session expired and could not be refreshed`**. Последний отказ был после свежего запуска Nightly около 17:04Z и Claude около 17:06Z, поэтому только долгоживущим старым процессом сбой не объясняется.

Добавленный путь восстановления и пауза собственных процессов не заявляются как доказанное устранение первопричины.

Проверки разделены: fixture-тесты запуска/блокировок/повторного входа и renderer восстановления диалога; настоящий установленный CLI проверяет только публичный status через Electron/preload/IPC, без model turn. ## Причина потери входа и постоянный токен — 2026-09-21

Пользователь сообщил, что вход слетал несколько раз. Разбор на этом компьютере (транскрипты `~/.claude/projects`, журналы Nightly, mtime файлов, строки бинарника CLI 2.1.278, ресурсы Claude Desktop):

- Все сбои (20.09 07:48Z и 17:07Z, 21.09 около 05:33Z) — первое обращение после многочасового простоя: access-токен (8 часов) истёк, CLI запросил refresh и получил `invalid_grant`. Ветка `tengu_oauth_refresh_token_marked_dead_invalid_grant` в CLI при этом **обнуляет** `accessToken`/`refreshToken` в `~/.claude/.credentials.json`, поэтому `auth status` затем показывает `loggedIn:false`.
- Refresh-токен одноразовый и ротируется. Один файл делят: CLI 2.1.278 (по процессу на вкладку CodexDesk, одновременный старт при восстановлении рабочего места), встроенный Claude Code Claude Desktop (`AppData\Roaming\Claude\claude-code.1.275\claude.exe`, тот же `~/.claude`; следы в `~/.claude/cache/model-catalog/tok-*-ccd.json` 20.09 20:06:35, за 43 с до отказа, и 21.09 09:11:02, через 34 с после входа), расширение VS Code 2.1.274, расширения Cursor 2.1.52/2.1.123. Простои 20–23 часа 16–19.09 без параллельных процессов проходили без отказов, серверный тайм-аут сессии не подтверждён.
- Известные открытые issue Anthropic: [#88583](https://github.com/anthropics/claude-code/issues/88583) (гонка параллельных сессий, обнуление credentials), [#94464](https://github.com/anthropics/claude-code/issues/94464) (встроенный Claude Code Desktop ротирует токен CLI), [#93014](https://github.com/anthropics/claude-code/issues/93014). Обход из #94464: `claude setup-token` и `CLAUDE_CODE_OAUTH_TOKEN`.

Реализация. **Настройки → Авторизация Claude Code → Постоянный токен для этого приложения**: кнопка «Получить токен: claude setup-token» открывает видимый терминал штатного CLI с `setup-token` (без остановки вкладок; CLI печатает строку `sk-ant-oat…`), поле принимает вставленный токен. `electron/claude-token.mjs`:

- `ClaudeTokenStore` хранит токен в `claude-token.json` userData, зашифрованный Electron `safeStorage` (DPAPI), с атомарной записью и режимом 0600; без доступного шифрования сохранение отклоняется. Формат проверяется (`sk-ant-oat NN-…`). В renderer уходят только `configured`/`savedAt`/`encryptionAvailable`/`error`; токен не попадает в `settings.json`, снимки рабочего места, диагностику и события.
- Токен передаётся как `CLAUDE_CODE_OAUTH_TOKEN` поверх унаследованного окружения **только** процессам Claude Code приложения: stream-транспорту вкладки (`ClaudeClient({ env })`), `claude auth status` и терминальному resume Claude. Консоли `auth login --claudeai` и `setup-token` получают обычное окружение, чтобы CLI выполнял реальный вход, а не отчитывался о токене. Настоящий CLI 2.1.278 с переменной отвечает `loggedIn:true, authMethod:oauth_token` без обращения к общему файлу.
- Сохранение/удаление перезапускает простаивающие вкладки Claude тем же путём, что и вход через браузер (события `auth` `opened`/`closed` с `message`); занятые вкладки применяют изменение при следующем подключении, их число возвращается в ответе IPC.
- `ClaudeLaunchGate` для вкладок без токена: старты процессов Claude и `usage/read` (первый запрос, вызывающий refresh после простоя) выполняются по одному; зависший предшественник ждётся не более 30 с. Codex не затрагивается.

Проверки: `tests/claude-token.test.mjs` (шифрование/ошибки чтения/недоступное шифрование, gate, окружение клиента, последовательный старт и usage через `WindowSession`, разделение окружений status/login/setup-token, аргументы терминала), расширенный `test:claude-auth-host` на production Electron с compiled fixture: отклонение Codex-сессий и неверных токенов, зашифрованный файл без открытого токена, перезапуск вкладки с переменной только у token-фазы, консоль `setup-token` без токена, удаление. Реальный `claude setup-token` требует браузера и не автоматизируется; прогноз для проверки на живом аккаунте: без токена и при запущенном Claude Desktop первое обращение после истечения access-токена вновь даст `OAuth session expired and could not be refreshed`.

## Возможности первой интеграции

- Текст, потоковый ответ и реально переданные CLI пояснения, изображения (из собственного attachment store), видимые пути документов, инструменты и результаты, вопросы/разрешения, остановка, очередь следующих сообщений.
- Нативная история Claude по папке и resume; ID в оболочке `claude:UUID`, CLI получает только UUID. В дереве проекта истории обоих агентов объединены, курсор содержит независимые позиции. Поиск названий и архив остаются Codex — UI это обозначает. Меню ⋮ у диалога Claude предлагает **переименование и удаление** (см. ниже); архива у нативной истории Claude нет, поэтому пункт «В архив» не показывается.
- Кнопка терминала открывает Claude `--resume UUID` с выбранными моделью/effort/access и той же cwd. Возврат перечитывает нативную историю. Существующий Codex resume путь сохранён.
- **Уточнение во время выполнения** («Уточнить») пишет ещё один user-frame в stdin работающего CLI. По документированному протоколу CLI вклеивает такое сообщение в текущий ход между вызовами инструментов, а `result` перечисляет все поглощённые `user_message_uuids`. Если сообщение пришло после последнего обращения к модели, CLI выполняет его следующим ходом без повторной отправки (`queued_turn_count > 0`): оболочка закрывает первый ход и открывает второй с uuid этого сообщения. Если счётчика нет, показывается ошибка «Claude не учёл уточнение», а не зависший ход. Остановка отправляет `interrupt` с `cancel_queued`, поэтому неучтённые уточнения отбрасываются вместе с ходом. До 16 уточнений на ход.
- **Сжатие контекста** отправляет штатную команду `/compact` отдельным ходом; скрытых инструкций нет. Граница сжатия (`compact_boundary`) показывается как элемент `contextCompaction`, вывод локальной команды — как пояснение. Пока сжатие идёт, уточнения отклоняются. Пустой диалог сжимать нельзя.
- **Переименование** открытого диалога использует control-запрос `rename_session` (`source: host`), закрытого — `renameSession` официального SDK в папке проекта. **Удаление** останавливает простаивающие CLI-процессы этого диалога, вызывает `deleteSession` SDK и блокирует дальнейшую запись по этому ID; вкладки закрывает renderer после подтверждения. Занятый диалог, ожидающие разрешения или открытый терминал блокируют операцию так же, как у Codex. Реализация — `electron/claude-threads.mjs`, маршрутизация по префиксу `claude:` в `host:manageThread`.
- **Окно перезапуска процесса.** Открытие диалога из истории заменяет CLI-процесс (`--resume`): старый завершается, новый запускается. В Nightly `8b6b6cd5df96` запрос списка истории, пришедший в это окно, отклонялся сообщением «Нет подключения к Claude CLI» (наблюдалось после запуска с восстановленной вкладкой Claude). Исправлено 2026-09-19: `thread/list` и чтение чужой истории обслуживаются из файлов без живого процесса, а остальные запросы ждут завершения замены (`_relaunch`) вместо отказа на старой сессии. Тест: `tests/claude-client.test.mjs`, «history reads stay available…».
- **Фазы текста.** Claude пишет пояснения между вызовами инструментов обычными текстовыми сообщениями без tool_use; раньше такой текст помечался `final_answer`, и таймер «Работал N с» останавливался на первом пояснении, хотя ход продолжался. С 2026-09-19 весь текст до `result` — `commentary` (виден в ходе работы), а при `result` последний текст хода переводится в `final_answer` и показывается ответом. Тест: «tool-less narration mid-turn stays commentary…».
- **Лимиты плана.** Слева от кэша в подвале composer у вкладки Claude показан «Лимит 5 ч: N %» — использование 5-часового окна claude.ai; наведение показывает время сброса, клик открывает все окна (неделя по всем моделям, Opus/Sonnet, интеграции, per-model из `model_scoped`) с полосками, временем сброса и кнопкой обновления. Данные — control-запрос `get_usage` (`skip_behaviors: true`, экспериментальный по документации SDK) при подключении и после каждого завершённого хода, плюс живые кадры `rate_limit_event` во время работы. Если лимиты недоступны (API-ключ, сторонний провайдер, старый CLI, ошибка) — показывается просто «Лимит», а клик отправляет штатную команду `/usage`, вывод которой приходит как пояснение CLI. Оболочка не считает лимиты сама и не хранит их между запусками. Реализация: `usage/read` в `electron/claude-client.mjs` (`normalizeUsage`), `src/UsageLimit.tsx`, состояние `usage` в `useCodex`; у Codex возможность `usage: false`, элемент не показывается.
- **Токены.** До 2026-09-19 `thread/tokenUsage/updated` для Claude приходил только вместе с `result`, причём «последний запрос» брался из `result.usage` — суммы за весь ход (несколько обращений к модели), из-за чего доля контекста завышалась, а во время работы счётчик показывал «нет данных». Теперь: `message_start`/`message_delta` дают живую оценку текущего обращения; каждый завершённый `assistant`-кадр с `message.usage` считается один раз по id сообщения (sibling-записи не дублируются) и обновляет `last` (входные = input + cache_read + cache_creation, как принято для оценки контекста) и накопительный `total`; при `result` `total` заменяется суммой `modelUsage` (накопительной для сессии, включая возобновлённую историю), `modelContextWindow` берётся оттуда же, а `last` остаётся последним обращением. `result.usage` используется только если ни одно обращение не сообщило usage. Токены размышлений API отдельно не отдаёт (`reasoningOutputTokens` не заполняется). Тест: «token usage is reported per model call…».
- **Токены и кэш при открытии истории — 2026-09-20.** До этого дня открытие сохранённого диалога Claude (в том числе восстановленной при запуске вкладки) показывало «Кэш: нет данных» и «Токены: нет данных»: ходы из транскрипта не имели `completedAt`, а счётчики токенов не читались. Теперь `claudeHistoryTurns` берёт `startedAt` из `timestamp` кадра пользователя и `completedAt` из последнего настоящего кадра ассистента хода; синтетический кадр ошибки API (`isApiErrorMessage`, модель `<synthetic>`, например истёкшая OAuth-сессия) переводит ход в `failed` с текстом ошибки и без времени завершения, поэтому оценка кэша для него остаётся неизвестной. `claudeHistoryUsage` считает `last` по последнему настоящему обращению и `total` по одному разу на `message.id` (sibling-кадры одного сообщения повторяют usage); транскрипт без usage даёт null, не нули. Снимок возвращается полем `tokenUsage` ответа `thread/resume` (не событием), renderer показывает его как есть и не считает живым ответом: таймер кэша по-прежнему берётся из `completedAt` через `historicalCacheActivity`. Восстановленные суммы засеивают `_usage.total`/`seen`, следующий `result` заменит их накопительным `modelUsage`. Проверки: `tests/claude-history.test.mjs` (метки времени, ошибка API, usage), `tests/claude-client.test.mjs` («resume returns the transcript token snapshot…»), сценарий в `scripts/ui-providers.mjs` (открытие «История Claude» показывает `4 512 токенов` и «Кэш ≈ 40:00», запросов модели нет). Чтение реальной истории этого проекта через SDK reader подтвердило время последнего ответа и counters без запуска CLI.
- **Навыки и MCP в настройках.** Метод `agent/capabilities` возвращает команды и навыки из ответа `initialize` (`commands` с признаком `builtin`), субагентов (`agents`) и состояние MCP-серверов через control-запрос `mcp_status` (`connected`/`failed`/`needs-auth`/`pending`/`disabled`, ошибки редактируются `safeText`). Блок «Действующие настройки» показывает число пользовательских навыков с раскрывающимся списком и состояние каждого сервера; запрашивается при открытии окна настроек, только чтение. Отказ `mcp_status` даёт сообщение, а не пустой список.
- MCP Claude используется через его настройки/CLI, редактор config Codex не применяется. Неизвестные interactive tool cards отклоняются с объяснением вместо безусловного allow.
- Steer/compact/rename проверены на fixture-протоколе по типам SDK 0.3.278 (`tests/claude-client.test.mjs`, `tests/claude-threads.test.mjs`); живой прогон с реальными запросами модели для этих трёх действий ещё не выполнялся.

## Доступ и изоляция

«Спрашивать разрешение» — Claude default permissions, «Разрешать правки» — acceptEdits, «Полный доступ» — bypassPermissions после обычного явного подтверждения. Это режимы Claude, не эмуляция filesystem sandbox Codex. Legacy read-only отображается как планирование (plan); inherited не переопределяет CLI. Новые вкладки и обычный restart не включают сохранённый full автоматически; специальный Nightly checkpoint сохраняет прежнюю семантику уже подтверждённого доступа.

`SettingsStore` хранит defaults отдельно в `providers.codex`/`providers.claude`. Прежние поля верхнего уровня принадлежат Codex, Claude не наследует его executable/model/effort/access. provider принадлежит host-сессии и не меняется через setSettings. Scoped RPC и resume отвергают ID другого агента; workspace snapshot сохраняет provider и namespace. Git/файлы/откат общие проектные функции и по-прежнему проверяют занятость всех сессий проекта.

## Реализация

- `electron/claude-client.mjs`: EventEmitter adapter к документированному SDK stream/control протоколу установленного CLI 2.1.278: `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --permission-prompt-tool stdio --permission-prompts host`. initialize/get_settings не отправляют model turn. set_model/apply_flag_settings/set_permission_mode меняют только сеанс.
- `can_use_tool` переводится в существующий UI approvals; ответ возвращает исходный updatedInput только после explicit allow. AskUserQuestion переводит выбранные/свободные ответы обратно. Неподдерживаемые управляющие запросы получают ошибку, а не approve.
- `electron/claude-history.mjs` лениво использует официальный `@anthropic-ai/claude-agent-sdk@0.3.278`: listSessions/getSessionInfo/getSessionMessages. Системные/служебные/зашифрованные блоки исключаются; текущая ветка истории восстанавливается SDK. Exact cwd, max 128 МиБ /100000 сообщений; CLAUDE_CONFIG_DIR наследуется как у CLI. Файлы истории и SQLite не переписываются.
- В сборку включён только self-contained SDK reader (sdk.mjs+README), выполнение использует установленный native CLI; optional bundled binaries не поставляются. Peers SDK устанавливаются npm для разработки, packaged history reader не вызывает API/query SDK.
- `AgentContext` задаёт имя агента UI. Bootstrap capabilities блокируют неподключённые функции; при ошибке Claude не происходит тихого возврата к Codex.

## Проверки

### Остановка без ложной ошибки — 2026-09-20

После «Стоп» Claude CLI может завершить ход кадром `result` с `subtype: error_during_execution`, `is_error: true` и строкой `[ede_diagnostic] result_type=user last_content_type=n/a stop_reason=tool_use`. Адаптер уже назначал такому ходу `interrupted`, но одновременно прикладывал `error`, из-за чего renderer показывал красную плашку и уведомление об ошибке. Теперь сообщение ошибки передаётся только для итогового статуса `failed`; пользовательская остановка завершается как `interrupted` без `error`. Ошибки без остановки, отказ управляющего запроса `interrupt` и обрыв процесса остаются видимыми.

Флаг остановки сохраняется до ожидания ответа control: CLI допускает ошибочный `result` раньше подтверждения `interrupt` (контракт SDK `interrupt_receipt_v1`). ### Публичные состояния фоновых задач

`task_started`, `task_progress`, `task_notification` преобразуются в `subAgentTask`: ID `task:<task_id>`, toolUseId, описание, статус, полученный summary и outputFile. Завершение фоновой задачи после основного ответа обновляет исходный turn. Native history запрашивает SDK `includeSystemMessages: true`, но адаптирует лишь эти публичные task кадры; вложенные assistant/parent_tool_use_id не раскрываются и не реконструируются. Тест проверяет позднюю ошибку, сохранение описания и отсутствие nested output. Сведения используются панелью подагентов.

SDK `forkSession` переписывает timestamp последнего скопированного assistant на текущее время, а `getSessionMessages` удаляет `forkedFrom`. Проверено на настоящем SDK с изолированной историей `artifacts/fork-sdk-ojSJao`: обычное чтение ошибочно давало бы свежий кэш без запроса модели. `ClaudeHistory.read` дополнительно использует официальный `importSessionToStore` с in-memory sink, собирая лишь UUID кадров с `forkedFrom`; их времена не считаются модельной активностью. Новый реальный ответ после fork снова даёт обычный таймер. Native transcript не редактируется, отдельный постоянный sidecar не создаётся. Если проверка происхождения недоступна из-за ошибки SDK, исторический таймер остаётся неизвестным. В UI первый fork также не показывает свежий кэш по скопированной истории.
