# Панель подагентов — 2026-09-20

Правая панель «Подагенты» собирает полученные задачи, состояния, ошибки и результаты в отдельные карточки. «К результату в чате» раскрывает ход работы и само событие инструмента, прокручивает к нему и ставит фокус. Для загруженной части истории можно запросить более ранние события. Панель не запускает агентов и не отправляет модельных запросов.

Codex: `collabAgentToolCall.receiverThreadIds/agentsStates` и `subAgentActivity.agentThreadId/agentPath`. Статус вызова инструмента не подменяет статус агента: завершённый `spawnAgent` может оставить агента `running`. `followupTask` обновляет задачу и очищает результат прежней работы при явном новом `running`; ошибки не маскируются общим уведомлением о завершении. Если CLI не прислал состояние, оно остаётся неизвестным.

Claude: публичные вызовы `Agent`/`Task` с `server: Claude` и параметры `description/prompt/subagent_type`, результат инструмента; для фоновых задач — `system.task_started/task_progress/task_notification`, преобразуемые в `subAgentTask` с `taskId/toolUseId`. Сообщения с `parent_tool_use_id` не раскрывают внутреннюю переписку подагента. Возвращённое управление после фонового запуска само по себе не означает завершения задачи. Результат связывается с исходным ходом, даже если он уже закончен. SDK history reader включает только поддерживаемые публичные task-кадры из системных сообщений; остальные служебные кадры исключены.

Реализация: `src/subagents.ts`, `src/SubagentPanel.tsx`, `src/useMessageJump.ts`, адаптер/reader Claude. Проверки: `tests/subagents.test.mjs`, тесты Claude client/history и `scripts/ui-work-log.mjs` (ошибка агента, точный переход к результату в свёрнутом ходе), снимок `artifacts/subagents-panel.png`. Это проверки событий на фикстурах; живой запуск подагентов модели в этой поставке не выполнялся.

## История: зависимые дочерние диалоги («поддиалоги») — 2026-10-09

Запрос: планировщик создаёт несколько исполнителей, и при нескольких группах боковая панель путает. Добавлено **отображение связи родитель → потомки**; действий над потомками, кроме уже существовавших, не добавлено.

### Что реально отдаёт протокол

Измерено на установленных Codex App Server **0.156.1** и Claude Agent SDK **0.3.278**; только `thread/list` и `thread/read`, без запросов модели. Аудит и сырые отчёты — [agent-c-subdialogs.md](agent-reports/agent-c-subdialogs.md).

- **`parentThreadId` в `thread/list` заполняется только при трёх условиях одновременно:** `sourceKinds` включает `subAgent*`, передан фильтр `cwd`, и **не** передан `useStateDbOnly: true`. На одном наборе: с `cwd` — 34 из 40 с родителем, с `useStateDbOnly:true` — 0 из 40, без `cwd` — 0 из 40. Поле заполняет разбор JSONL, а не state DB; ни одно из трёх условий нельзя убрать как оптимизацию.
- **`forkedFromId` в `thread/list` не приходит никогда** (0 во всех вариантах, включая известное ответвление). Есть только в `thread/read`.
- **`sessionId` всегда равен `id`** и в `thread/list`, и в `thread/read`. Корень дерева сессий, записанный в rollout `session_meta.session_id`, через протокол не отдаётся — **как ключ группировки непригоден**, группировка по нему придумала бы связь.
- **`source` — достоверный дискриминатор вида связи, и он есть в `thread/list`:** `{subAgent:{thread_spawn:{…}}}` — исполнитель; `{subAgent:{other:"guardian"}}` — служебное ревью; `"vscode"`/`"cli"`/`"appServer"` — верхний уровень. Регистр ключей на проводе смешанный (внешний camelCase `subAgent`, внутренний snake_case `thread_spawn`), разбор принимает оба варианта.
- `sourceKinds: ['subAgent']` и `['subAgentOther']` вернули **идентичные множества** — фильтр источников исполнителей от служебных не отделяет, отделяет только разбор `source`.
- **Claude Code связей не сообщает вовсе:** `SDKSessionInfo` (единственный тип `listSessions`/`getSessionInfo`) не содержит ни родителя, ни источника ответвления, ни дерева сессий. Сам факт остаётся верным; формулировка «Связи недоступны» показывалась до 2026-10-09 и заменена нейтральным «Без группы» — см. раздел «Группы диалогов» ниже.

### Модель

`src/thread-relations.ts` — чистая логика без IPC и React. `parentId` берётся **только** из `parentThreadId`, при его отсутствии — из `forkedFromId`. Заголовок, время, `cwd` и порядок в списке источником связи не являются. `evidence` фиксирует, каким полем доказана связь. `kind`: `root` / `spawn` / `service` / `fork` / `unavailable`. `label` — `agentNickname`, иначе `agentRole`, иначе `agent_path`; если backend ничего не дал, подписи нет.

`buildRelationGroups` группирует потомков по **прямому** родителю, поэтому несколько планировщиков дают несколько независимых групп и никогда не сливаются. Потомок, чей родитель отсутствует в загруженных списках, получает собственную группу с подписью «Родительский диалог не загружен» и **не** прикрепляется к похожему родителю. Глубина больше одного поддерживается: прямым родителем может быть сам потомок.

Служебные потоки (`guardian`, `review`, `compact`) не показываются как исполнители: они сохраняются и считаются отдельно, под свёрнутой строкой «Служебные диалоги агента: N». Причина измерена — 247 из 379 локальных rollout и 135 из 141 связанных диалогов этого проекта являются автоматическими guardian-ревью без `agentNickname`; без разделения панель заполнилась бы строками «The following is the Codex agent history whose request action…».

### Интерфейс

Два представления, оба только навигационные.

- **Дерево проекта.** У строки родителя появляется счётчик исполнителей и disclosure; потомки рисуются под ним с отступом, значком агента и подписью агента. Группы свёрнуты по умолчанию, состояние хранится по `projectKey|parentId`, поэтому переключение вкладок его не сбрасывает.
- **Панель «Подагенты»** — переключатель рядом с «Архивом», панель поверх списка проектов. Карточки групп по всем зарегистрированным папкам. С 2026-10-09 панель называется «Группы», а строка «Связи недоступны» заменена на «Без группы» — см. раздел ниже.

Меню ⋮ у строк потомков показывает **тот же** набор действий с теми же блокировками `threadLocked`; новых пунктов и никаких разрушающих действий не добавлено.

### Границы: архив, поиск, пагинация, массовый выбор

- **Пагинация истории папки не изменена.** Составной курсор `desk:{cwd,codex,claude}` остался прежним. Потомки читаются **отдельным** `host:listThreadChildren` со своим курсором, только когда папка раскрыта или открыта панель «Подагенты». Это сознательный отказ от подмешивания потомков в основной список: страница из 40 записей заполнилась бы служебными потоками, а `nextCursor` папки перестал бы соответствовать видимому.
- **Архив.** `archived` в запросе не задаётся, поэтому протокол возвращает только неархивные потоки и архивный потомок не может вернуться в панель этим путём. Сама панель архива сохраняет прежнюю плоскую группировку по папкам: `listArchivedThreads` использует интерактивные `sourceKinds`, потомков в ней нет. Семантика `archive`/`delete` для потомков не менялась: подтверждение удаления уже предупреждает о дочерних диалогах, а `ThreadActionCoordinator` уже проверяет занятость потомков по цепочке `parentThreadId`.
- **Поиск.** `thread/list` с `searchTerm` использует интерактивные `sourceKinds`, поэтому потомки в результатах не появляются и вложенность к ним не применяется — поведение поиска не изменено. Чип родителя в результатах **не добавлен** сознательно: у интерактивных диалогов `parentThreadId` всегда пуст, и такой элемент никогда бы не отобразился.
- **Массовый выбор.** Названная область осталась прежней — «загруженная история одной папки» или «загруженные результаты одного поиска». Строки потомков в `rows` не входят, «Выбрать все» их не считает, и в режиме выбора они отображаются без чекбокса и без перехода (`.relation-child-inert`).
- Кнопка «Обновить диалоги» папки теперь перечитывает и историю, и связи. Ошибка чтения связей показывается отдельной строкой с «Повторить» и **не** затрагивает загруженную историю папки.

## История: группы диалогов — 2026-10-09

Уточнение пользователя: нужна **организация диалогов и удобное отслеживание**, а не
доказательство нативного родства. Строгая модель связей сохранена и продолжает работать
там, где Codex сообщает `parentThreadId`; поверх неё добавлены **пользовательские группы**,
работающие одинаково для Codex и Claude. Подробности — [agent-c-grouping.md](agent-reports/agent-c-grouping.md).

Группа — это собственная метаданная оболочки: стабильный локальный ID `g-<uuid>`, видимое
имя, рабочая папка, необязательный главный диалог и список участников. Один диалог состоит
максимум в одной группе. Хранилище — `electron/thread-groups.mjs` → `thread-groups.json` в
userData канала: атомарная запись (`wx` + rename, 0600), последовательная очередь, проверка
имени/папки/идентификаторов, пределы 200 групп и 500 участников, повреждённый или чужой по
версии файл не перезаписывается и не считается пустым. Транскрипты CLI, SQLite, нативные
данные Claude и `config.toml` Codex не читаются и не изменяются; сами агенты о группах не
знают, и в терминальном `codex`/`claude --resume` диалог остаётся обычным.

Действия: ⋮ папки → «Новая группа диалогов…»; ⋮ диалога → «В новую группу…», «В группу «…»»,
«Убрать из группы»; ⋮ группы → «Переименовать группу…», «Удалить группу…»; `+` в заголовке
группы открывает новый диалог, который вступит в неё, как только получит ID (то есть после
первой отправки). Удаление группы убирает только группировку — диалоги, история, вкладки и
черновики остаются и возвращаются в «Без группы».

Диалоги, созданные вне приложения, попадают в «Без группы» до явного назначения. **Пока в
папке нет ни одной группы, боковая панель выглядит ровно как прежде**: одна секция без
заголовка, плоский список в прежнем порядке. Пагинация, поиск, архив, массовый выбор,
переименование, ответвление и вкладки не изменены; участники вне загруженных страниц
показаны числом, а не угадываются.

Прежняя формулировка «Связи недоступны: Claude Code не сообщает родителя диалога» удалена из
интерфейса и кода: диалог Claude просто лежит в «Без группы», пока его не сгруппируют.
Панель «Подагенты» переименована в «Группы» и показывает пользовательские группы, «Без
группы» и отдельной карточкой нативных подагентов Codex. Если зависимый диалог явно добавлен
в группу, он перестаёт вкладываться под нативного родителя — один диалог всегда в одном месте.

`npm run test:groups` (`scripts/ui-conversation-groups.mjs`, production renderer, 15 блоков).

## Агенты-исполнители — 2026-10-10

### История: fork-сабдиалоги — 2026-10-10

Решение владельца: **контекст родителя исполнителю не передаётся никогда.** Прежние «сабдиалоги»
создавались через `thread/fork` с копией истории и модальным выбором модели/глубины; и то и другое
убрано. Агент-исполнитель — обычный новый пустой диалог той же папки, открываемый как
`open(cwd, undefined, provider, undefined, { childOf, childLabel })`. Собственный `thread/fork`
функции «Ответвить» не затронут. Подробности — [agent-a-executor-agents.md](agent-reports/agent-a-executor-agents.md).

Связь хранится только в `electron/thread-child-links.mjs` (`thread-child-links.json`) и
дописывается, когда диалог получает ID после первой отправки. Добавлено необязательное поле
`label` (≤200 символов, без переводов строк и `\0`); версия файла осталась `1`, записи без `label`
остаются валидными. Нативные `parentThreadId`/`forkedFromId` App Server в ряд исполнителей по-прежнему
не попадают: служебные guardian/review/compact — внутренности агента, а не исполнители пользователя.

Три точки входа, все создают одно и то же: кнопка с иконкой `Bot` 15px на активной вкладке родителя,
кнопка «+ Исполнитель» в конце ряда и команда «Новый агент-исполнитель» в палитре Ctrl+K. Создание
блокируется только `opening`/`actionBusy`: **занятость родителя помехой не является**, потому что
чистый диалог его не трогает. Глубина строго 1 — у исполнителя обеих кнопок создания нет, а команда
палитры у него отключена с пояснением.

Имена по умолчанию — «Агент A», «Агент B», …: следующая свободная латинская буква среди исполнителей
этого родителя, считая по связям и по открытым вкладкам (`src/executor-agents.ts`, чистая логика без
React и IPC; после Z идёт AA). Освободившаяся буква переиспользуется, произвольно переименованный
диалог букву не занимает. До первой отправки имя живёт подписью вкладки; получив `threadId`, оболочка
пишет его названием диалога обычным `manageThread` `rename` и в `label` связи. Переименование
выполняется **первый раз, когда исполнитель освободился**: `assertIdle` отклоняет rename работающего
диалога, поэтому попытка повторяется на следующем отчёте состояния, а не форсируется.

Ряд «Исполнители» виден и у родителя, и у открытого исполнителя; активный подсвечен. Текст 11px,
высота ряда 38px, цвета по `Kuzmich_Design_System.md` (`bg-primary` фон, `border-subtle` разделитель,
`bg-surface-muted` у активного, `accent-muted-green`/`accent-green-soft` у значков). Вкладка
исполнителя в основном ряду не показывается; вкладка, ещё не получившая `threadId`, адресуется по
`sessionId`, иначе её нельзя было бы выбрать обратно.

Не изменялись: нативные подагенты (`src/subagents.ts`, `SubagentPanel.tsx`), панель «Группы»,
«Ответвить», портал, архив, поиск и пагинация истории.

### Закрытие, родитель и состояние исполнителей — 2026-10-11

Крестик открытой подвкладки закрывает её CLI-процесс, сохраняя беседу и связь с родителем.
У работающего исполнителя доступны «Остановить и закрыть» и «Дождаться и закрыть».
Второе действие ждёт принятого `turn/completed` с любым итогом, а не просто сброса `busy`:
потеря соединения тоже сбрасывает занятость и не доказывает завершения хода. Пометка видна
значком таймера и подсказкой «Закроется по завершении»; повторный клик предлагает отменить
ожидание или остановить сразу. **Пометка хранится только в памяти приложения и теряется
при перезапуске**; снимок рабочего места и `thread-child-links.json` её не сохраняют.

Новый вопрос или запрос разрешения отменяет отложенное закрытие до обработки завершения;
проверяется и текущее `pending > 0`. Исполнитель остаётся открытым и виден в колокольчике,
пока ждёт ответа. Чтобы закрыть его после ответа автоматически, ожидание нужно выбрать
заново. `completedTurnRevision` в `SessionSummary` учитывает принятые завершения,
`pendingKind` берётся из актуальных запросов: просмотр вкладки убирает непрочитанное,
но не превращает неотвеченный вопрос в обычное разрешение.
Незавершённый запрос снимается по ответу пользователя или `serverRequest/resolved`, а не
самим `turn/completed`. Это совпадает с транспортом Codex; адаптер Claude перед завершением
хода отдельно отправляет `serverRequest/resolved` для оставшихся запросов. Разрыв соединения
и смена диалога по-прежнему очищают запросы. Во время отложенного закрытия очередь ставится
на паузу, новые отправки и автопинги блокируются: следующий ход не должен стартовать между
завершением текущего и закрытием. Отмена пометки сама по себе очередь не возобновляет.

После закрытия вкладки сохранённая запись остаётся в ряду с серой точкой «Вкладка закрыта»
и собственным крестиком «Убрать из ряда (диалог останется в папке)». Это существующий
`unlink` с теми же блокировками, что у «Отвязать от родителя»; ни беседа, ни история не
удаляются. Недоступный крестик объясняет причину в подсказке, а отказ уже начатого действия
показывается сообщением. Блокировки закрытия одинаковы у основного ряда и подвкладок.

Подвкладка получает живые `busy`, `pending`, `loading`, `connection`, `terminalOpen` и
непрочитанное из открытой сессии. Во время работы `Bot` сменяется спиннером. Приоритет
состояния — ожидание, работа, ошибка подключения; вопрос отмечается «?», разрешение —
жёлтой точкой, завершение в фоне — точкой непрочитанного. Записи без `sessionId` живого
состояния не имеют. Подсказка словами поясняет состояние, поэтому цвет не единственный
способ различить его.

При активном исполнителе в основном ряду выделен ровно его родитель (`child-active`):
фон активной вкладки и более мягкая акцентная полоса. Метка `Bot` с коротким именем
исполнителя декоративна, полное имя включено в доступное имя кнопки. Если кто-то из
исполнителей ждёт ответа или имеет непрочитанный вопрос, эта же метка становится жёлтой;
если никто не ждёт, но кто-то работает — зелёной со спиннером вместо `Bot`; завершение в
фоне оставляет в ней точку непрочитанного, пока исполнителя не открыли. Без открытого
исполнителя метка показывает число ждущих или работающих, а подсказка перечисляет их
поимённо — ряд `Исполнители` рисуется внутри родителя, и из других вкладок эта метка
единственная сообщает о работе. Клик переключает на родителя. Если его вкладка закрыта,
показывается навигационная вкладка родителя без отдельного CLI-процесса; только нажатие
открывает родителя через существующий `openParentThread`.

Стили подвкладок и состояния родителя поддерживают обе темы, включая
`[data-theme=kuzmich]`. Нативные подагенты, глубина 1, отсутствие передачи контекста,
формат и версия хранилища связей и allowlist IPC-мутаций сохранены.

### Каскадное закрытие и открытие из дерева — 2026-10-12

Две доработки по замечаниям владельца; модель не вызывалась, реальные диалоги не изменялись.

**1. Крестик родителя закрывает группу.** Прежде `close()` закрывал только родителя, а вкладки
исполнителей оставались скрытыми в `tabs` (в основном ряду их нет), и при активном исполнителе
рисовалась навигационная вкладка `missingParent` без крестика. Теперь `requestClose` учитывает
`tabs` с `childOf === threadId` родителя:

- все простаивают — `closeGroup` закрывает исполнителей, затем родителя, без подтверждения;
- кто-то работает или грузится — один общий диалог с «Отмена» / «Дождаться и закрыть» /
  «Остановить и закрыть»; существующие подтверждения одиночной вкладки сохранены;
- «Дождаться и закрыть» помечает всю группу в `deferredClose` (таймер и пауза очереди) и
  добавляет `cascadeClose = { parentId, ids, awaited }`. Пер-вкладочный эффект участников
  каскада пропускает, поэтому они закрываются только вместе и только после принятого
  `turn/completed` каждого работавшего участника. Потеря соединения завершением не считается;
- вопрос или запрос разрешения у любого участника отменяет каскад целиком (`cancelCloseWait`
  вызывается и из `onSessionAttention`, и по `pending` в эффекте);
- `closeBlockedReason` родителя теперь учитывает терминал исполнителя и называет его имя;
- `closingGroup` не даёт закрыть участника дважды, а отказ хоста на ребёнке останавливает
  каскад, оставляя родителя открытым с видимой ошибкой;
- `restoreClosed` возвращает исполнителя под родителя: `childOf`/`childLabel` берутся из
  сохранившейся связи, иначе вкладка вернулась бы отдельной верхней;
- «Закрыть остальные» закрывает подвкладки раньше родителей и щадит родителя, у которого
  осталась открытая подвкладка; `closeProject` закрывает всё по `cwd` — исполнитель лежит в
  той же папке.

**2. Открытие исполнителя из дерева.** Вложенная строка звала `controls.openThread`, то есть
`open()` без `childOf`: появлялась независимая верхняя вкладка и дубль в ряду «Исполнители».
Теперь строка вызывает `openChildThread` (он же `openExecutor`), который activate-ит открытую
вкладку, иначе открывает родителя (`openParentThread`, фокус тут же забирает сам исполнитель) и
только потом исполнителя с `childOf`. `openChildThread`/`openParentThread` объявлены в
`ProjectTreeControls`; `openExecutor` и `openParentThread` стали асинхронными. Дубль устранён
независимо от пути: в `src/App.tsx` ряд дедуплицируется по `thread.id`, а не только по
`sessionId`, и запись связи без `sessionId` дополняется живым состоянием этой вкладки.

Проверки: `npm run test:executors` — каскад с простаивающим и с работающим исполнителем (все
три кнопки диалога), таймер у крестика родителя и подвкладки, закрытие группы по
`turn/completed`, отмена ожидания вопросом исполнителя, блокировка терминалом исполнителя,
«Закрыть остальные» без сирот, порядок восстановления родитель → исполнитель, открытие
исполнителя из дерева (родитель открывается сам, фокус на агенте, дубля нет, повторный клик
активирует существующую вкладку без нового процесса). `npm run test:executor-nav` — вкладка
`missingParent` для родителя, ушедшего в архив при открытом исполнителе: процесс не создаётся
до нажатия, нажатие открывает родителя обычным `thread/resume`. Снимки:
`artifacts/executor-open-from-tree.png`, `artifacts/executor-cascade-close.png`,
`artifacts/executor-cascade-closed.png`, `artifacts/executor-missing-parent.png`.

Прогон 2026-10-12: `npm run check` (tsc, Node-тесты, vite build), `test:executors`,

## «Отправить агенту», навигация и вложенность — 2026-10-10

Владелец работает дирижёром: агент родительского диалога пишет промты для исполнителей
fenced-блоками кода. Header такого блока (`markdown-code-header` в `src/Markdown.tsx`) получил кнопку
«Отправить агенту» рядом с «Копировать». Нажатие создаёт исполнителя текущего диалога и переносит
текст блока **черновиком композера** — тем же механизмом `open(..., { draft })`, которым пользуется
передача задачи другому агенту. **Автоотправки нет**: пользователь читает промт в композере, при
необходимости правит и отправляет сам. Вложения не переносятся.

Видимость кнопки прокинута пропсом `onSendToExecutor` сверху вниз (`App` → `Conversation` →
`Message` → `Markdown` → `CodeBlock`), без глобального состояния. Её нет: в архиве (`ArchiveView`
просто не передаёт проп), в панели подагентов, у исполнителя (глубина 1 — `canCreateExecutor`
ложно), на сообщениях пользователя и в неактивной вкладке.

Хлебные крошки исполнителя: «папка › **имя родителя** › заголовок». Имя родителя берётся из
`threadTitle` (имена из `manageThread`, загруженная история, заголовок открытой вкладки). Клик
активирует вкладку родителя, если она открыта, иначе открывает диалог заново обычным `resume`;
`thread/fork` при этом не запрашивается и связи не трогаются.

ПКМ по подвкладке исполнителя открывает меню (`src/ExecutorTabMenu.tsx`, те же блокировки, что в
`ThreadMenu`: `opening`/`actionBusy`/`threadLocked`):

- **Переименовать** — обычный `manageThread` `rename` плюс запись нового имени в `label` связи, чтобы
  ряд и выбор следующей свободной буквы не расходились.
- **Отвязать от родителя** — удаление записи связи и только её. Диалог остаётся в папке обычным, его
  вкладка возвращается в основной ряд. Сам диалог не трогается: `manageThread` не вызывается.
- **В архив** — обычный архив; вместе с ним связь удаляется, иначе в ряду остался бы безымянный
  призрак диалога, которого в папке уже нет. Восстановленный из архива диалог возвращается обычным.
- **Закрыть вкладку** — единственный пункт, доступный исполнителю, который ещё ничего не отправил:
  диалога у него пока нет, переименовывать, отвязывать и архивировать нечего.

В дереве проекта (`src/ProjectTree.tsx`) исполнитель — обычный диалог той же папки, поэтому он
приходит той же страницей истории. Страница дедуплицируется по `id`, исполнители вкладываются под
своего родителя с отступом и направляющей, а раскрытость хранится по ключу `projectKey|parentId`
(`expandedGroups`). Раскрывает детей **бейдж-счётчик** у родителя: это кнопка с `aria-expanded` и
подписью «Развернуть N агентов-исполнителей диалога …». Исполнитель, родителя которого нет на
загруженной странице, остаётся в плоском списке — из дерева ничего не пропадает молча. В режиме
множественного выбора список плоский, и область выбора остаётся прежней: загруженная история папки.

Хранилище: `ThreadChildLinkStore.manage({ action: 'unlink' | 'relabel' })`, IPC
`host:manageThreadChildLink`. Отвязанный, заархивированный и удалённый исполнитель исчезает из ряда и
из дерева сразу — локальная копия связей чистится вместе с вызовом хоста. Предупреждение при удалении
родителя («Codex также удалит связанные дочерние диалоги») не изменялось.

Проверки: `tests/thread-child-links.test.mjs` — случай отвязки (точечное удаление, идемпотентность,
переживание перезагрузки, `relabel` с валидацией, отказ неизвестной операции и неверного id);
`npm run test:executor-nav` — `scripts/ui-executor-nav.mjs`, production renderer в Edge с подставным
scoped bridge. Снимки: `artifacts/executor-send.png`, `artifacts/executor-tree.png`.
Подробности и прогон — [agent-c-executor-nav.md](agent-reports/agent-c-executor-nav.md).


## Пробуждение после фоновой задачи Claude — 2026-10-11

Измерено на живой сессии Кузьмича: после завершения фонового подагента Claude CLI сам вставляет user-кадр `<task-notification>` и продолжает работу без пользователя. Кузьмич это продолжение молча отбрасывал (`_frame` в `electron/claude-client.mjs`: кадры без активного хода), поэтому владелец видел молчание до собственного сообщения, хотя готовый ответ уже лежал в нативной истории.

Исправление: финальный task-кадр при простое ставит флаг `_wakePending`; user-кадр с `<task-notification>` (или первый assistant-кадр при ожидающем пробуждении) открывает новый ход `auto: true`; echo хода показывает сводку задачи, а не сырой кадр; result такого хода принимается и при несовпадении uuid. Реплеи resume ходов не создают — до первой отправки `session.sent` ложен. Codex не затронут: у него механизма пробуждения нет, для него остаётся автопинок оболочки (отложено). Тесты: три случая «wake» в `tests/claude-client.test.mjs`.
