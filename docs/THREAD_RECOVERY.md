# Открытие диалога и конфликт записи — 2026-09-18

Симптом: при открытии `thread not found`, пустой чат; при отправке `thread … already has an active writer`. В `useCodex.resume()` выбранный ID сохранялся до RPC, а ошибка оставляла его доступным для `turn/start`, хотя подключение диалога не подтверждено. Дополнительно `Promise.all` страниц items/turns скрывал доступные сообщения при ошибке только метаданных ходов.

## Проверенные факты

- Диалог `01a0ae2f-319d-7991-8cc4-64c522c1b1b3` существует: настоящий Codex `0.154.0` прочитал `thread/read(includeTurns:true)` с 41 ходом, `thread/items/list` и `thread/turns/list`. `historyMode:'paginated'`, состояние отдельного reader — `notLoaded`. История не потеряна.
- Это уточняет прежнее ограничение [AI_CONTEXT.md](AI_CONTEXT.md): раньше paginated был проверен только схемами, теперь чтение и resume проверены настоящим CLI. Схемы по-прежнему сгенерированы старой `0.154.0-alpha.6.2`.
- Копия rollout в отдельном `CODEX_HOME` успешно открывается с `excludeTurns:true` и `false`, включая повторный resume. Сам `excludeTurns` причиной не оказался.
- Два настоящих App Server с одним изолированным `CODEX_HOME` воспроизводят `already has an active writer` (`-32600`). При этом чтение истории вторым процессом работает, а после завершения владельца повторный resume успешен. Нельзя обходить блокировку удалением lock-файла или переписыванием базы.
- У исходного диалога обнаружена настоящая OS-блокировка `thread-writer-locks/<id>.lock`. Она исчезла одновременно с внешним процессом VS Code, пока исходные процессы Desk оставались живы. Точный PID-владелец не установлен; это корреляция. Первоначальный `thread not found` отдельно не воспроизведён.
- Для нового пустого paginated-диалога до перезапуска CLI может отвечать на полный read `list_turns is not supported yet` (`-32601`); это не доказательство отсутствия сохранённой переписки.

## Исправление

`src/useCodex.ts` хранит отдельно выбранный диалог и подтверждённое подключение (`resumedThreadRef`, `threadReady`). После ошибки resume читает сохранённую историю через штатный `thread/read`, сохраняет ID и черновик. UI сообщает «Диалог не подключён» и предлагает «Повторить подключение». Попытка отправки сначала повторяет resume; без успеха не сохраняет изображения, не создаёт optimistic message и не вызывает `turn/start` или новый `thread/start`. Пинг, compact и терминал требуют подтверждённого подключения. Конфликт writer поясняется по-русски: закрыть тот же диалог в другом сеансе и повторить подключение.

Страницы items и метаданных turns обрабатываются независимо. Ошибка turns не скрывает доступную страницу; ошибка items использует полный read без нового resume. Активность учитывается сразу из resume, до чтения страниц. Sequence защищает от результатов старого resume после отключения; свежие live items сохраняют приоритет над историей, а старый snapshot при повторном открытии не перекрывает обновлённые сообщения. При переходе от полного read к последней странице после retry ранее загруженные старые сообщения остаются перед ней; отдельная browser-проверка утверждает хронологический порядок и отсутствие дублей.

История, авторизация, конфигурация и модель/effort пользователя не менялись; внутренние SQLite-базы вручную не редактировались. Model turns для проверки не отправлялись. В изолированных native fixtures модель/провайдер переопределялись только для их собственного bootstrap без обращения к модели.

## Переподключение одной кнопкой — 2026-09-19

При `connection === 'error'` кнопка в строке ошибки называется «Переподключить диалог», если диалог выбран, и «Подключить» иначе. `useCodex.reconnect()` перезапускает транспорт через `connect(undefined, { keepThread: true })`: вместо `clearThread()` вызывается `detachThread()`, который сбрасывает живое состояние (активный ход, ожидающие разрешения, compact, кэш, `threadReady`) и ставит очередь на паузу, но оставляет выбранный диалог, видимые сообщения и черновик. После успешного bootstrap тот же ID возобновляется штатным `resume(previous, true)`; `turn/start` не отправляется, writer-lock не обходится. «Переподключить» в настройках по-прежнему выполняет полный сброс — это осознанно сохранено для сценариев смены папки/исполняемого файла.
