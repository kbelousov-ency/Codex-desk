# Кэш и автопинг — 2026-09-17

Запрос пользователя: счётчик холодного кэша и сообщение в чат за минуту до предполагаемого остывания для поддержания кэша. Изначально при неизвестном сроке был принят настраиваемый исходный срок 5 минут. Пользователь уточнил «по умолчанию час»: текущий default — 60 минут, автопинг за 1 минуту до срока (через 59 минут). Пометка «оценка» сохранена: это настройка пользователя, не измеренный TTL локального router.

## Подтверждённые сведения

Прочитаны [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching/) и [Codex App Server](https://developers.openai.com/codex/app-server/). В актуальной документации lifetime зависит от модели/режима: для in_memory обычно 5–10 минут неактивности, до часа; другие режимы имеют иные сроки. Повторное использование prefix может обновлять срок, но сохранение конкретного prefix не гарантируется. Эти сведения не устанавливают TTL стороннего провайдера router и не являются поводом менять конфигурацию модели.

Локальная схема `protocol/v2/TokenUsageBreakdown.ts`: `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningOutputTokens`, `totalTokens`; `ThreadTokenUsage` содержит `last`, `total`, `modelContextWindow`. Данных о времени истечения в этом событии нет. UI показывает реальные `last.inputTokens - last.cachedInputTokens` как «Без кэша» (включает cache-write), cachedInputTokens как «Из кэша», cacheWriteInputTokens отдельно если >0. Отсутствующие поля не заменяются нулями. Нельзя называть каждую некэшированную часть доказанным cold start.

## Устройство

- `src/useCodex.ts` отдаёт `cacheActivityAt`, `cacheGeneration`, `cacheTurnCompleted`, `sendPing`. Свежесть определяется живыми model deltas/usage/completed model items текущего turn; команды и история не освежают. Успешный turn/completed — fallback только если за turn не было model-сигналов. Долгая команда после model response не сдвигает таймер до своего завершения.
- Остановка/ошибка/отключение/clear/resume/model/effort/access/reroute инвалидируют оценку. Синхронные refs состояния и sendSequence защищают от отправки между рендерами и от поздних результатов предыдущей отправки; settled/current turn IDs отделяют запоздалые события. Загрузка старой истории не используется как свидетельство свежего кэша.
- `src/useCacheKeepAlive.ts` держит настройки и таймер конкретной смонтированной вкладки. TTL 2…1440 минут, начальное 60; `CACHE_PING_LEAD_MS=60000`. Каждый новый hook начинает с `enabled=false`. Не сохраняем enabled в глобальные settings и не наследуем во вновь созданные вкладки: платные запросы включаются пользователем отдельно.
- Пинг по умолчанию: `Пинг для поддержания кэша. Ответь только «ОК», без инструментов и изменений файлов.` Текст показан в редактируемом поле до включения. Это userMessage через обычный turn/start в существующем thread с теми же моделью/effort/access; никакого developer prompt или прямого API. Команда `sendPing` не создаёт новую беседу и не использует composer draft/attachments. Модель может не выполнить просьбу; применяются обычные события/подтверждения.
- Автопинг запрещён при busy/loading/disconnected/pending approvals, чтении вложений или смене настроек. Принятие turn/start не считается обновлением кэша: fence `{generation,completed}` ждёт завершения, предотвращая серию повторных отправок. Ошибка/Stop/смена параметров выключает автопинг. После истечения срока нет catch-up; явный «Пинг сейчас» доступен в простаивающей беседе.
- `src/CacheControl.tsx` отображает оценочный countdown, фактические токены, TTL, checkbox, видимый текст, ручной пинг, число отправленных пингов. Поля настроек живут только до закрытия вкладки/перезапуска. Отдельные IPC-методы не нужны.
- В Electron `backgroundThrottling:false` поддерживает таймер при свёрнутом окне; сон/задержки ОС не компенсируются запросами задним числом. Закрытие окна по-прежнему завершает собственные App Server процессы, таймеры unmount очищаются.

## Отсчёт при открытии истории — 2026-09-18

По уточнению пользователя старая беседа теперь восстанавливает оценку от последнего ответа, а не получает новый час при открытии. Прежнее правило «история не используется» выше заменено только для достоверного времени из истории. `ThreadItem` не содержит timestamp, поэтому используется `Turn.completedAt` в Unix-секундах последнего успешного запроса. Это приблизительное время последнего ответа; UI явно поясняет источник и показывает дату/время в настройках кэша.

`src/cache-history.ts` учитывает порядок: legacy/full thread.turns по возрастанию, `thread/turns/list` с sortDirection:desc — последний ход первым. `thread.updatedAt` не используется: переименование и изменение метаданных не означают ответ модели. Если последний ход interrupted/failed/inProgress, содержит error или contextCompaction, либо нет timestamp/есть будущее/некорректное время, оценка остаётся неизвестной. Для paginated model item проверяется по отдельной загруженной странице items; при отсутствии model item неизвестное не подменяется успешной генерацией. Старый успешный ход не подставляется вместо последнего неуспешного. Истёкший timestamp сохраняется и показывает «Кэш: возможно остыл».

При resume счётчики sequence/lifecycle/cacheRevision не позволяют поздней истории заменить свежую дельту или отменённую оценку после ошибки/остановки/reroute. Повторное открытие той же беседы инвалидирует прежнюю оценку и выключает ранее включённый автопинг. Снапшоты tokenUsage/item.completed и отдельные replay turn.completed при загрузке не считаются живым ответом; реально полученная дельта имеет приоритет. Завершённые загруженные turn ID добавляются в settled guards. Чтение старых страниц не двигает таймер. Read fallback после writer conflict может показать сохранённое время, но пинг недоступен до подтверждённого resume.

Открытие истории не включает автопинг и не отправляет сообщений. Если пользователь сам включил его в оставшуюся минуту, применяется прежний порог. После истечения часа автоматического «догоняющего» запроса нет. Живые ответы по-прежнему используют время последнего model signal; долгая команда после него не обновляет оценку временем завершения команды.

Проверки: `tests/cache-history.test.mjs`, `test:cache-history` (production UI, подставной bridge и управляемые часы), `test:cache-history-host` (Electron/preload/IPC и отдельный JSONL fixture). Старые сценарии `test:cache`, `test:resume` сохраняются. Никаких реальных model turns для проверки таймера.

## Подробности токенов по наведению

`src/TokenUsage.tsx` заменяет статичный счётчик. Hover/focus открывает portal-панель, нажатие закрепляет, pin-button открепляет, Escape/крестик/клик снаружи закрывают. Задержка закрытия 180ms позволяет перевести курсор с кнопки на панель. Закрепление снимается при смене вкладки/диалога; данные не смешиваются. Popover ограничен viewport и прокручивается независимо. Подпись счётчика сохраняет смысл `last.totalTokens`, известный 0 показан как `0 токенов`, неизвестное — «Токены: нет данных».

`src/token-metrics.ts` валидирует nonnegative safe integer, неизвестное остаётся null. `last` и `total` раздельны. Производные: `uncachedInputTokens=input-cached` (включает запись), `ordinaryInputTokens=input-cached-write`, `nonReasoningOutputTokens=output-reasoning`, `cachedSharePercent=cached/input`. Вычисления только при известных согласованных данных. Исходный totalTokens не пересчитывается суммой вложенных строк. Некорректные/противоречивые поля подсвечены, не дают отрицательную «экономию». Последний вход / modelContextWindow обозначен сравнением последнего запроса с лимитом, не точным заполнением текущего контекста.

Пользователь просил состав кэша и возможную экономию, если запустить compact. Повторно прочитаны официальные Prompt caching и App Server docs: кэш — повторно использованный prefix; API сообщает численные counters, без долей по файлам/AGENTS/истории/инструментам. `contextCompaction` item имеет только id, `thread/compact/start` запускает асинхронное сжатие и возвращает {}, прогноза нет. Поэтому панель честно пишет, что состав и будущая экономия неизвестны. Нельзя выдавать сумму total по диалогу или символы видимых сообщений за размер удаляемого контекста; compact сам может расходовать токены и менять prefix, прошлый расход не возвращает. Нового запуска compact/API override не добавлено, hover/pin только отображают данные.

`tests/token-metrics.test.mjs`: 6 проверок валидных, нулевых, отсутствующих, неверных, противоречивых данных и context proxy >100%; весь набор 63 tests прошёл. UI regression `scripts/ui-token-details.mjs` прошла: hover/transit/pin/keyboard, размеры1440/940/650, zero/missing, точные last/total и изоляция, без модели. При откреплении кнопкой внутри popup фокус возвращается счётчику, иначе focus удерживал незакреплённое окно после ухода мыши. На узких экранах тест закрывает штатную правую overlay-панель, чтобы счётчик был доступен.

На этом этапе сборка `release/token-details/win-unpacked/Codex Desk.exe` была активна через active-build.txt. Packaged smoke с настоящим Codex подтвердил Astra/Ultra, 6 моделей, дерево и PNG без model turn. Renderer в app.asar сверён с проверенным dist. ## Кнопка compact вместо пояснения

По следующему запросу пользователя прежнее решение «только информация, без запуска» заменено: из окна токенов удалён блок о возможной экономии и добавлена кнопка «Сжать контекст /compact». Та же операция доступна командой `/compact`; устройство и проверки — [COMMANDS.md](COMMANDS.md). Ограничение протокола о неизвестной будущей экономии сохраняется, но отдельный поясняющий блок в popup больше не нужен. Hover/pin по-прежнему ничего не запускают.

Compact инвалидирует оценку свежести и выключает автопинг. Повторный запуск запрещён до завершения операции. Если после compact не пришло новое `thread/tokenUsage/updated`, `last` сбрасывается в null, а `total` и `modelContextWindow` сохраняются: прежний размер входа нельзя показывать как новый размер после сжатия. Состав кэша и числовые counters остаются без выдуманного прогноза.
