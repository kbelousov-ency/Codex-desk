# Release и Nightly

С 2026-09-18 вместо отдельной папки под каждый запрос используются два постоянных канала:

- `release/stable/Codex Desk.exe` — проверенная версия. Обычный `Codex Desk.lnk` / `Start Codex Desk.vbs` всегда запускает её.
- `release/nightly/Codex Desk.exe` — новые изменения. Отдельный `Codex Desk Nightly.lnk` / `Start Codex Desk Nightly.vbs`.
- `release/stable-previous/` — максимум одна предыдущая стабильная сборка для отката, появляется после следующего продвижения.

`active-build.txt` больше не выбирает запускаемую версию. Сборка Nightly не переключает обычный ярлык. Прежние тематические пути в заметках описывают историю проверок; удаление старых exe не делает эти решения устаревшими.

Исходники ведутся в Git: `https://github.com/kbelousov-ency/Codex-desk`, ветка `main`, remote `origin`. Репозиторий инициализирован по запросу пользователя после первого подтверждённого продвижения Nightly в Release. Прежние заметки об отсутствии `.git` описывают состояние до 2026-09-18. Сборки, зависимости, тестовые профили/артефакты, журналы и персональные ярлыки в Git не включаются; канал Release обновляется отдельно от отправки исходников.

## Обязательный рабочий процесс

1. Изменить исходники и выполнить проверки.
2. `npm.cmd run package` (или `package:nightly`) обновляет **только Nightly**. Произвольный `--config.directories.output=...` отклоняется.
3. Проверить Nightly, включая packaged smoke с `CODEX_DESK_PACKAGED` равным абсолютному пути Nightly exe. Проверка UI/протокола без модели отделена от реальных model turns.
4. Пользователь проверяет изменения. **Продвигать в Release только после явного подтверждения пользователя.** Разрешение на обычную задачу или сборку Nightly не означает разрешение продвигать её в Release.
5. `npm.cmd run release:promote` проверяет целостность и копирует проверенные байты Nightly в Release; renderer/host не пересобираются. Меняется только внешний marker канала. Старая Release становится единственной `stable-previous`.
6. При необходимости `npm.cmd run release:rollback` возвращает предыдущую Release; требует закрытого стабильного приложения.

При первоначальном переходе создание первого Release разрешено самим запросом пользователя внедрить два канала. Последующие изменения идут только в Nightly до отдельного подтверждения.

Для замены Release нужно закрыть его приложение. Первоначально это требовалось и для Nightly; по следующему запросу добавлено [автоматическое применение Nightly](#автоматическое-применение-nightly). Временная упаковка находится под `artifacts/channel-build` и очищается после успешной публикации. Блокировка и транзакционное переименование защищают от одновременных операций и неполной замены; неподтверждённые изменения не должны попадать в stable.

## Автоматическое применение Nightly

Пользователь разрешил автоматический перезапуск текущей НБ для применения готовых изменений. `npm.cmd run package` теперь может собирать при запущенном Nightly. Собранный и проверенный по контрольным суммам кандидат помещается в единственную `artifacts/nightly-update/app`, отдельный скрытый Node-helper запускается detached, а команда сборки завершается. Это необходимо, когда сам Codex выполняет сборку внутри обновляемого приложения: нельзя синхронно ждать завершения собственного model turn.

Helper ждёт завершения задач во всех вкладках, запросов разрешений, compact, операций MCP/истории и закрытия переданного терминала. Renderer дополнительно откладывает снимок до окончания чтения картинок/отправки и незавершённых диалогов настроек/переименования. Пока работа продолжается, показывается уведомление. После готовности окно временно блокируется, сохраняет вкладки/порядок/активную вкладку, выбранные диалоги, черновики, вложения и настройки; Nightly завершается штатно. Helper ждёт завершения main и остальных Electron-процессов, проверяет кандидат повторно, транзакционно заменяет nightly и запускает новый exe с прежними cwd/userData. Работающий пользовательский процесс принудительно не завершается. Release не участвует.

Восстановление читает обычную историю через App Server и не отправляет «Продолжай» либо другой скрытый prompt. Ранее выбранные модель/effort/access сохраняются для этого специального перезапуска, включая уже подтверждённый full access. При обычном запуске прежнее правило подтверждения full остаётся. Автопинг после перезапуска выключен; оценка кэша восстанавливается обычным чтением истории. Новая пустая вкладка и несохранённое сообщение сохраняются без создания model turn.

В `electron/nightly-update.mjs` — локальный Windows named pipe со случайным токеном и owner-pipe для защиты регистрации, без HTTP listener. `release/.nightly-instance.json` принадлежит только запущенному Nightly; `mode:0600` на POSIX, Windows наследует разрешения папки, системные ACL не меняются. Сообщения status/prepare/cancel ограничены и не принимают пути или команды. Срок подготовленного снимка без подтверждения помощника — 30 секунд; исчезновение helper освобождает интерфейс. При запуске нескольких тестовых профилей один не перехватывает регистрацию другого.

`electron/main.mjs` резервирует операции на время подготовки, проверяет sender/окно/ID и принимает снимок только в ожидаемом запросе. `electron/update-checkpoint.mjs` атомарно сохраняет `nightly-update-workspace.json` в данных Nightly; сведения о cwd/executable берёт из host сессий. Снимок содержит несохранённые пользовательские черновики/картинки (они могут содержать личную информацию), но не экспортируется в диагностику. Загруженная переписка и config туда не копируются. После подтверждения восстановления renderer снимок удаляется. Операции save/clear сериализованы; generation и блокировка storage не позволяют старой подготовке стереть новый снимок.

Если обновление не удалось, текущий канал сохраняется либо восстанавливается прежней транзакцией; единственный кандидат остаётся для повторной попытки: `node scripts/apply-nightly-update.mjs`. Удалить неработающую очередь без изменения установленных каналов: `node scripts/apply-nightly-update.mjs --discard` (при работающем helper отказ). Следующая сборка не затирает ожидающую. Технический журнал без токенов/черновиков — `artifacts/nightly-update.log`. Подтверждённое намерение перезапуска сохраняется в queue state, поэтому повтор после ошибки установки также запускает Nightly. Предел ожидания busy — 7 дней; завершения уже подготовленного процесса — 120 секунд. При ошибке запуска готового exe используется обычный ярлык.

Для первой установки механизма старый Nightly нужно закрыть один раз: в нём ещё нет службы обновления. Дальнейшие штатные сборки применяются автоматически. Распространяемая коллегам папка без исходников и Node не собирает себя сама; механизм предназначен для локальной разработки через команду package, а не автоматической реакции на каждое сохранение исходника.

Проверенная поставка механизма: Nightly build ID `865c482f18f0d050de28ed10fde7dfc02f7c6cea7960fc0f28002d9d0dac886c`; Release остался `74e2c7c166098278d75de1987e9ed1035b24aebd5e2763baf537959a21f1ea47`. 198 Node-тестов прошли, один Windows file-symlink skipped. Проверены renderer restore, tabs/resume/access/cache, packaged bootstrap с настоящим Codex без model turn. `test:nightly-update-host` использует полную отдельную копию exe в `artifacts/nightly-update-host-ieuqIu`, JSONL fixture и настоящий helper: ожидание активного хода, замена файлов, новый PID, восстановление двух вкладок/активного диалога/черновика/картинки/access, повторное чтение снимка из восстановленного renderer без скрытого продолжения. 21 актуальный host/preload/dist файл в итоговом app.asar совпадает с исходниками и dist. ## Идентификация и данные

В интерфейсе и заголовке окна указаны RELEASE / NIGHTLY / DEV. Наведение на бейдж и окно «Диагностика» показывают версию, короткий build ID и дату. `electron/build-info.json` внутри app.asar хранит version/buildId/builtAt, внешний `resources/channel.json` определяет канал. `release-manifest.json` позволяет проверять содержимое поставки перед продвижением; общая product version пока `0.1.0`, точную поставку отличает SHA-256.

Stable сохраняет прежний userData `%APPDATA%/Codex Desk`. Nightly использует `%APPDATA%/Codex Desk Nightly`, development — `%APPDATA%/Codex Desk Development`. При первом запуске Nightly копируются только собственные settings.json/workspace.json без перезаписи существующих файлов; затем настройки, проекты, Chromium storage и журналы каналов независимы. Тестовый `CODEX_DESK_DATA_DIR` полностью изолирует инициализацию и attachments.

Авторизация, конфигурация, MCP и история установленного Codex остаются общими. Это **не** изолированная тестовая копия Codex: работа в Nightly и явное сохранение MCP используют тот же Codex config. Одновременная запись одной беседы двумя каналами по-прежнему ограничивается штатной writer-lock; не обходить её. Новые и старые изображения лежат в прежнем `%APPDATA%/Codex Desk/attachments`, потому что история Codex ссылается на абсолютные пути; перенос не должен ломать изображения. Свою SQLite/rollout базу оболочка не создаёт и не переписывает.

## Очистка старых сборок

Пользователь явно разрешил убрать прежние многочисленные релизы. `scripts/cleanup-releases.ps1` содержит фиксированный список 24 старых каталогов и трогает только непосредственных детей release, после появления обоих новых каналов. Проверяет границы, тип сборки, отсутствие ссылок/junctions и запущенных процессов. Не удаляет stable/nightly/stable-previous и неизвестные каталоги. `npm.cmd run release:cleanup` делает одну попытку; служебный `-WaitForExit` ждёт освобождения используемой старой сборки и удаляет её после закрытия окна. Фоновой помощник запускается скрытым, без завершения пользовательского приложения.
