# Контракт обновлений через Router Portal

Статус документа: read-only исследование, 2026-10-14. Production-каталог и
публикации не изменялись.

Цель контракта — безопасно проверить и скачать установщик Кузьмича из Portal,
сохранив существующую авторизацию и различая номер версии приложения и номер
сборки Jenkins.

## Что проверено

### Живой Portal

Проверка выполнена с существующим пользовательским ключом роутера, прочитанным
в main process из уже настроенного Codex подключения. Ключ и его значение не
выводились, не записывались в примеры и не использовался ключ `apps:publish`.

Адрес Portal: `https://coder-portal.encycam.com`.

`GET /api/apps/codex-desk` с `Authorization: Bearer <обычный пользовательский ключ>`
вернул `200 application/json`. Обезличенная фактическая форма ответа:

```json
{
  "slug": "codex-desk",
  "title": "Кузьмич",
  "summary": "Десктоп-приложение для работы с Codex и Claude Code — вкладки, история, терминал, вход через Portal в один клик",
  "instructions": "обычный текст установки и подключения; отдельного release notes поля нет",
  "features": ["console", "mcp", "skills", "windows"],
  "owner_email": "<обезличено>",
  "updated_at": "2026-10-12T08:29:39.848149+00:00",
  "versions": [
    {
      "version": "0.11.0",
      "filename": "Codex-Desk-Setup-0.11.0.exe",
      "size_bytes": 101875916,
      "sha256": "63b686f84b03a5111aade7b5064bc244216946ec5122a85cc8081b3ace1eaebb",
      "created_at": "2026-10-12T08:30:01.173457+00:00",
      "url": "/api/apps/codex-desk/versions/0.11.0/file"
    }
  ]
}
```

Установщик в живом ответе присутствует как запись `versions[]`. Отдельных
`available`, `is_installer`, `channel`, `build_number`, `build_id`,
`release_notes` или абсолютного `download_url` нет. `summary` и `instructions`
описывают приложение/установку целиком, а не конкретный выпуск.

Порядок версий нельзя трактовать как порядок SemVer. В текущем исходнике
Portal `list_versions()` сортирует записи по `created_at DESC` — самая свежая
заливка сверху. Номер версии является строкой автора и сам по себе не
сортируется.

`url` — относительный путь. Его можно разрешать только относительно
зафиксированного origin `https://coder-portal.encycam.com`; host, userinfo,
query и fragment из ответа нельзя принимать.

### Авторизация и HTTP-поведение

Проверены следующие read-only запросы:

| Запрос | Результат |
| --- | --- |
| Карточка с обычным router bearer | `200` |
| Карточка без авторизации | `401` |
| Карточка с заведомо неверным bearer | `401` |
| Файл версии с bearer | `401` |
| Файл версии без авторизации | `401` |
| `http://coder-portal.encycam.com/api/apps/codex-desk` | `308` на HTTPS |
| HTTPS-карточка с завершающим `/` | `307` на путь без `/` |

Последние два ответа получены с `redirect: manual`; тело и секреты не
сохранялись. Для запроса с Bearer к файлу сервер не дошёл до проверки версии:
поэтому этот результат не является проверкой существования файла.

В локальном Portal-исходнике `GET /api/apps/{slug}` и
`GET /api/apps/{slug}/versions/{version}/file` используют `get_current_user`,
то есть Portal session-cookie. В том же исходнике bearer используется для
операций автора/CI (`author()`), а не для download. Различие между живой
карточкой (Bearer принимает) и живым download (Bearer отвергается) сохранено как
расхождение deployed API с доступным исходником; на это нельзя закрывать глаза
в реализации.

Из исходника подтверждено: если cookie-сессия уже прошла авторизацию, запись
версии отсутствует или файл пропал с диска, download возвращает `404`; имя
файла берётся из базы. Неправильный формат slug/version даёт `400`.

`403` для этих GET-ручек живым обычным чтением не воспроизведён. В проекте
`403` относится к проверке прав (`require(...)`) и CSRF/мутациям. Для клиента
`403` означает «доступ запрещён»: не повторять автоматически и не подменять
его `401`.

Временную аварию Portal намеренно не создавали. Существующий
`PortalSessionService` задаёт timeout 15 секунд, запрещает редиректы
(`redirect: "error"`) и выдаёт безопасное общее сообщение для сетевого сбоя,
не передавая raw error в UI. Для updater нужны те же границы: bounded timeout,
ограничение JSON-ответа, отмена запроса при выходе и ограниченный повтор только
для timeout/сетевых ошибок/5xx.

## Правильный источник авторизации

У Кузьмича уже есть авторизованный Portal-контур:

- постоянный Electron partition `persist:kuzmich-portal`;
- вход внутри `PortalAuthWindow`, cookies остаются в main process;
- `PortalSessionService` делает запросы с `credentials: "include"`,
  `redirect: "error"`, без ручного `Cookie` заголовка;
- status/key ручки — `GET /api/me` и `GET /api/key`; ключ роутера хранится
  только host-side и выдаётся renderer только обезличенным состоянием;
- router credentials в `router-connections.json` зашифрованы Electron
  `safeStorage`/Windows DPAPI и не являются авторизацией download Portal.

Проверка карточки может использовать обычный пользовательский router bearer,
если это поддерживает фактически развернутый route. Проверка и скачивание должны
использовать Portal-cookie из `session.fromPartition(PORTAL_PARTITION)`, пока
сервер явно не расширит read/download auth. Запросы не должны попадать в
`shell.openExternal`: shell сам по себе не переносит Bearer приложения и не
гарантирует cookie из изолированного Electron partition.

Одной авторизованной Portal-сессии недостаточно для допуска к обновлению:
перед проверкой клиент обязан получить свежий `PortalSessionService.status()` и
требовать `state === "signed-in"`, `keyState === "approved"` и разрешённый
продукт Кузьмича в `products`. Состояния `none`, `pending`, `held-elsewhere`,
отсутствующая entitlement или истёкшая сессия означают отсутствие доступа к
роутеру: каталог и установщик не запрашивать, а показать существующий путь
входа/подключения. Сам router bearer не передавать в download, пока Portal не
подтвердит такую авторизацию для этой ручки.

Авторизованный download для реализации:

1. В main process получить карточку через Portal session.
2. Разрешить относительный `url` относительно фиксированного origin и сверить
   slug/version с выбранной записью.
3. Выполнить GET тем же Portal session с `credentials: "include"`,
   `redirect: "error"` и timeout.
4. Поток записать во временный файл, проверить фактический размер и SHA-256 с
   `size_bytes`/`sha256`, затем атомарно переименовать в staging-файл.
5. Только после явного действия пользователя открыть локальный файл/установщик.
   Не передавать URL во внешний браузер до авторизованного скачивания.

## Каналы выпуска и версия

Подтверждено по текущему репозиторию Кузьмича:

- `package.json` сейчас содержит `0.11.0` и принимает стабильную форму
  `X.Y.Z`.
- `scripts/package.mjs` собирает Nightly/Experimental 3; stable получается
  отдельным promotion-процессом.
- `experimental3` — отдельный `Kuzmich.exe`, профиль и router-only режим;
  его установщик именуется `Kuzmich-Setup-X.Y.Z.exe`.
- stable сохраняет установщик `Codex-Desk-Setup-X.Y.Z.exe` и текущий
  `AppUpdateService` разрешает сетевые public updates только для
  `channel === "stable"`. Nightly/Development не должны принимать чужой
  public Release.
- Упакованный `electron/build-info.json` уже содержит `version`, `buildId` и
  `builtAt`; `buildId` — SHA-256 отпечаток файлов/branding, а не Jenkins
  `BUILD_NUMBER`. Старые установки могут не иметь этого файла/поля.

Внутренняя модель для нового клиента:

```text
version       = X.Y.Z                         (package.json, обязательна)
buildNumber   = положительное целое или null   (Jenkins BUILD_NUMBER)
catalogVersion = X.Y.Z.BUILD_NUMBER           (только если buildNumber известен)
buildId       = 64 hex или null                (immutable content identity)
channel       = stable | nightly | experimental3 | development
```

Сравнение кандидатов:

1. Сначала численно сравнить `X.Y.Z`.
2. При одинаковом `X.Y.Z`, если у обеих сборок есть `buildNumber`, сравнить его
   численно.
3. У старой установки без `buildNumber` (`null`) кандидат той же `X.Y.Z` с
   известным номером считается требующим обновления: старый клиент не может
   доказать, что уже содержит эту сборку.
4. Кандидат без номера не должен вытеснять установку с известным номером той
   же базовой версии.
5. Если `buildNumber` отсутствует и у текущего клиента, и у кандидата, равная
   `X.Y.Z` не считается обновлением.
6. Сравнивать строки `0.11.0.10` и `0.11.0.9` лексикографически нельзя.

Текущий ответ Portal не содержит `buildNumber`, `buildId` или `channel`, а
`version` в нём — только `0.11.0`. Поэтому по существующему ответу невозможно
доказать, что две заливки с одной `X.Y.Z` различаются, и невозможно безопасно
отфильтровать смешанные каналы.

## Ошибки, которые должен видеть updater

- `401`: Portal-сессия истекла/отсутствует. Сбросить transient auth state,
  показать «Войдите в Portal», не использовать router bearer как обход и не
  повторять в tight loop.
- `403`: доступ запрещён политикой/прокси/CSRF. Не повторять автоматически;
  показать безопасное сообщение и сохранить текущую установку.
- `404` карточки: приложение/каталог отсутствует. Считать сервисный контракт
  несовместимым, а не «обновлений нет».
- `404` download: версия или файл отсутствуют. Удалить staging-файл и показать
  «установщик недоступен»; повторять только после новой проверки карточки.
- `400`: некорректный slug/version или повреждённый запрос. Это ошибка
  контракта/данных, без повторов.
- timeout, DNS/TLS/connection reset и `5xx`: временная недоступность. Не
  удалять рабочую установку; разрешить ручной повтор с bounded backoff.
- redirect: отклонить ответ. Нельзя автоматически отправлять cookies или
  Bearer на другой origin.
- несоответствие `size_bytes` или SHA-256: считать артефакт повреждённым,
  удалить staging и не запускать установщик.

## Пробелы и минимальное дополнение

Для cookie-авторизованного host-fetch отдельное новое endpoint не требуется:
существуют карточка и download, а существующий Portal partition уже является
источником авторизации.

Но текущего ответа недостаточно для строгого Jenkins-контракта и смешанных
каналов. Доказательство — live `versions[]` содержит только `version`,
`filename`, `size_bytes`, `sha256`, `created_at`, `url`; в нём нет build/channel/
release-note идентификаторов, а локальный `build-info.json` не знает Jenkins
`BUILD_NUMBER`.

Минимальное additive-дополнение к объекту `versions[]` (без нового endpoint):

```json
{
  "build_number": 1234,
  "build_id": "<64 lowercase hex>",
  "channel": "stable",
  "release_notes": "<bounded plain text>"
}
```

Для старых записей все четыре поля должны быть отсутствующими или `null`.
Публикационный pipeline обязан записывать `build_number = BUILD_NUMBER`,
`build_id` из `electron/build-info.json`, `channel` фактического канала и
release-specific notes. До подтверждения этого pipeline клиент не имеет права
выдумывать build number из времени заливки или порядка массива.

Если требуется скачивание без активной Portal-cookie, минимальный серверный
вариант — разрешить обычный пользовательский router bearer на GET download той
же проверкой владельца/профиля, либо выдать одноразовый короткоживущий signed
URL. Это отдельное изменение доступа; ключ `apps:publish` для клиента не нужен.

## Что уже можно реализовать

- host-side discovery через существующую Portal session и фиксированный origin;
- строгую проверку формы карточки, размера, SHA-256 и безопасного относительного
  URL;
- численное сравнение `X.Y.Z`, выбор кандидата независимо от порядка массива и
  сохранение текущего установщика при любой ошибке;
- скачивание в staging с cookie, отказ от redirect и проверку целостности;
- безопасные состояния для `401`, `403`, `404`, timeout, `5xx` и повреждённого
  файла;
- совместимость старых установок без `buildNumber` через `null` и правила выше;
- запрет обновления Nightly/Development/Experimental 3 из неподходящего
  stable-канала до появления подтверждённого `channel` в каталоге.

Нельзя считать подтверждёнными до изменения/проверки pipeline: реальный Jenkins
формат `X.Y.Z.BUILD_NUMBER` в поле `version`, соответствие имени установщика
четырёхкомпонентной версии, выдачу `build_number/build_id/channel/release_notes`,
успешный cookie-auth download в живой сессии и live-ответ `403`/`404`/временной
аварии. Эти места оставлены явными, чтобы не превращать предположение в API.
