# Пульт в Telegram Mini App — план v2

Дата: 2026-10-14. Статус: **план, код не начат**. Основа — действующий
[контракт удалённого управления v1](REMOTE_CONTROL_CONTRACT.md) и реализованный
[личный Telegram-бот](TELEGRAM.md). Исходный черновик внешнего ассистента переработан
по решениям владельца; служебные пометки (`citeturn…`) удалены.

## Решения владельца — 2026-10-14

1. **Заменить** личного бота новой схемой «общий бот + Mini App + relay-сервер».
   Замена выполняется только после паритета возможностей: выбор беседы, отправка
   текста, состояние, последний ответ, остановка. До паритета личный бот работает.
2. Продукт **для многих пользователей**, не только для владельца. Нужны общий бот,
   backend с базой и relay.
3. **Создание вкладок с телефона в первую версию не входит.** Запрет контракта v1
   («удалёнка не создаёт и не открывает беседы») сохраняется; снятие запрета —
   отдельное явное решение владельца на этапе расширения.
4. **На сервер уходят только идентификаторы и названия разрешённых открытых вкладок**
   (плюс агент, короткое имя проекта, статус, длина очереди). Текст переписки,
   ответы модели, пути, настройки и журналы на сервере не хранятся.
5. **Все разрешения выдаются только на компьютере.** Доступ к каждой беседе —
   default off, включается на ПК; с телефона нельзя выдать, расширить или передать
   доступ. Отзыв — тоже только с ПК.
6. **Надёжность доставки прорабатывается сквозно**: идемпотентность от Mini App до
   существующего ledger ядра, без слепых повторов (раздел «Доставка» ниже).

## Архитектура

```text
Telegram Mini App ⇄ HTTPS/WSS ⇄ Backend + relay ⇄ исходящее WSS ⇄ Кузьмич (bridge)
                                   │
                                   └─ Bot API → уведомления в Telegram
```

- Telegram никогда не подключается к ПК напрямую. Кузьмич сам держит исходящее
  защищённое соединение с relay: работает за NAT, без открытых портов, переживает
  переподключения.
- Кузьмич — источник истины для вкладок, окон, разрешений и очередей. Сервер только
  маршрутизирует команды и хранит минимум для отображения (п. 4).
- Bot token общего бота живёт только на backend. На ПК токена больше нет вовсе.

## Что переиспользуется из готового

Ядро агента 1 остаётся без замены, меняется только транспорт:

- `RemoteControl` facade и `remote-control-store`: grants с `grantId`/`generation`/
  `runtimeId`, durable операции с неизменяемым `requestId`/payload, фазы
  `received…uncertain`, fail-closed при повреждении хранилища.
- Выстраданные правила доставки: потеря ACK ≠ отказ, адресат доказывается записью,
  повтор «на удачу» запрещён, сверка через read-only `getOperation` до повторного
  `execute`.
- Per-thread переключатель доступа (`TelegramThreadAccess`) и каркас настроек
  (`PhoneAccessSettings`) перерабатываются: вместо токена бота — pairing с сервером
  и отзыв устройства.

Заменяется: `electron/telegram/*` (long polling, личный токен, карточки бота) —
после этапа 5 выводится из поставки.

## Что разрабатывается

**Backend.** Сущности: Telegram-пользователь; установка Кузьмича (несколько на
пользователя); desktop-сессия/окно; вкладка с постоянным `tab_id`; pairing-сессия;
команда с `command_id`, статусом (`accepted`/`executed`/`failed`/`uncertain`)
и результатом; права и настройки уведомлений. Интерфейсы: авторизация Mini App
(криптопроверка `initData`, `initDataUnsafe` не доверять); список установок и
вкладок; команды к вкладке; WebSocket событий; pairing и отзыв устройства;
heartbeat/presence; повторы после reconnect; rate limit; журнал действий.

**Bridge в Кузьмиче.** Исходящее WSS; отдельный отзывной credential устройства
(не bot token); reconnect и heartbeat; приём команд; публикация snapshot и событий
**только по разрешённым на ПК вкладкам**; исполнение через существующий
`RemoteControl`; локальный отзыв/отключение устройства. `tab_id` назначается при
создании вкладки на ПК, до появления `thread_id`, чтобы адрес был стабилен.

**Mini App, первая версия.** Состояние подключения Кузьмича; список установок и
разрешённых вкладок (название, агент, проект, статус, активность); карточка вкладки:
отправить текст, состояние, последний ответ, остановить с подтверждением конкретного
хода; экраны «офлайн»/ошибки; настройки уведомлений и отвязка устройства.
Полный терминал и история переписки в Mini App не переносятся.

**Общий бот.** Только уведомления через Bot API: задача завершена, Кузьмич отключился,
команда не выполнена, требуется действие на компьютере. Не поток токенов и не каждое
изменение текста. `sendData`/`answerWebAppQuery` основным транспортом не являются.
Открытие — Main Mini App / кнопка меню / ссылки `startapp` для pairing.

## Pairing

QR или одноразовый код с высокоэнтропийным nonce, показанный **только на ПК**,
с подтверждением с обеих сторон (код из URL пересылаем — одного его мало).
Срок жизни и лимит попыток — как у действующего pairing (10 минут, 5 попыток).
Pairing даёт телефону личность, но не даёт доступа ни к одной вкладке (п. 5).

## Доставка и идемпотентность (п. 6)

- `command_id` создаёт клиент; backend хранит статус команды; bridge передаёт её ядру
  как `requestId` в namespace вида `ma:<user>:<installation>:<command_id>`. Повтор того
  же `command_id` возвращает ту же durable операцию, второй отправки нет; другой
  payload при том же ID — конфликт.
- Relay доставляет «как минимум один раз», поэтому после reconnect bridge сначала
  сверяет сохранённый `requestId` через `getOperation` и только при доказанном
  `not_found` вызывает `execute` — ровно как действующий бот.
- Неопределённый исход (`uncertain`) не превращается ни в отказ, ни в авто-повтор;
  пользователь видит «требуется проверка на компьютере».
- После reconnect — полный resync snapshot; события несут монотонную ревизию,
  устаревшие отбрасываются. Статус команды на сервере обновляется только
  подтверждением от bridge, не таймером.

## Приватность (п. 4)

| Уходит на сервер | Никогда не уходит |
| --- | --- |
| `tab_id`, название разрешённой вкладки, агент, короткое имя проекта, статус, длина очереди, presence установки | Текст переписки и ответов, вложения, пути/cwd, журналы, настройки, approvals, bot/OAuth-токены ПК |

Команды и их итоговые статусы хранятся на сервере ограниченный срок (журнал),
текст команды — только до подтверждения исполнения, затем удаляется, как в
действующем журнале бота.

## Безопасность (п. 5 и контракт v1)

Проверка `initData` на сервере; короткоживущая сессия Mini App; отдельный отзывной
credential каждой установки; pairing с истечением срока; ACL по владельцу, запрет
чужих `installation_id`/`tab_id`; rate limit; журнал pairing, отвязок и удалённых
действий; шифрование секретов; подтверждение опасных операций локальными правилами
Кузьмича; никаких методов выдачи прав, смены модели или ответов на approvals
в серверном API — как в facade v1.

## Разработка и тестирование без сервера

Mini App — обычная веб-страница; Telegram открывает её внутри чата и передаёт
`initData`. Делается тем же стеком, что и интерфейс Кузьмича: React + Vite +
TypeScript. Подключение Telegram — штатный `telegram-web-app.js`
(`Telegram.WebApp`) или SDK `@telegram-apps`.

Лестница тестирования, до продакшена нужны только первые две ступени:

1. **Браузер на ПК.** Страница открывается как обычный сайт, объект
   `Telegram.WebApp` и `initData` подставляются фикстурой. Проверяется весь UI,
   экраны ошибок и офлайна. Backend и relay — локальные процессы, bridge Кузьмича
   подключается к `ws://localhost`. Это же — основа автоматических тестов.
2. **Туннель с ПК + тестовый бот.** Telegram требует HTTPS-ссылку из интернета;
   её даёт туннель (cloudflared или ngrok) на локальный backend. У BotFather
   заводится отдельный тестовый бот, ему прописывается ссылка туннеля — и настоящее
   Mini App открывается на настоящем телефоне, пока всё (backend, база, relay,
   Кузьмич) работает на ПК разработчика. Ссылка у бота меняется в любой момент.
   Уведомления работают без входящей ссылки: бот сам ходит к Bot API, webhook на
   этом этапе не нужен (можно long polling).
3. **Сервер** — только после прохождения ступени 2, для доступа других людей.

Отладка внутри Telegram: в Telegram Desktop включается режим отладки с веб-инспектором
Mini App; на Android — инспекция WebView через USB. Проверка `initData` пишется и
тестируется на фикстурах с известным токеном тестового бота. Отдельная тестовая
среда Telegram (отдельный аккаунт, допускает HTTP) — опциональна; для этого плана
достаточно тестового бота и туннеля.

Домен с HTTPS, backend, база данных, WSS relay, webhook Bot API, мониторинг,

## Решения приёмки этапов 0–2 — 2026-10-14

- **Аутентификация установки — Ed25519 вместо общего секрета.** Исходные поручения
  противоречили друг другу: HMAC по сырому `deviceSecret` (контракт А) нельзя проверить
  по hash-only хранилищу (поручение В). Решение: ключевая пара создаётся на ПК при
  pairing, приватный ключ никогда не покидает ПК, сервер хранит только публичный ключ;
  `hello.proof` — подпись challenge. Контракт обновляется до 2.1 агентом А.
- Решения владельца: QR — пакет `qrcode`; поле `queuePaused` добавляется восьмым
  в snapshot; несколько установок — просто список, без «основной»; имя установки
  предлагается при привязке, по умолчанию «Кузьмич».
- `TabSummary` сервера принимает все поля wire-контракта (включая `queueLength`,
  `updatedAt`, `queuePaused`): все они входят в утверждённый список решения № 4.

## Как продолжить после перерыва — памятка на 2026-10-15

Состояние на вечер 2026-10-14: этапы 0–3 сданы и **проверены вживую** (см. этапы выше).

Чтобы снова поднять стенд:

1. Запустить `relay-server/start-live.cmd`, ввести token бота (BotFather → `/mybots` →
   бот → API Token) и username `ENCY_Kuzmich_bot`. Окно не закрывать: оно держит
   relay и туннель.
2. Бесплатный туннель выдаёт **новый адрес при каждом запуске**. Поэтому каждый раз:
   - новую `https://…trycloudflare.com/` отдать BotFather (Bot Settings → Configure
     Mini App → Enable Mini App → прислать ссылку);
   - в Кузьмиче, «Подключение к серверу», вписать **только origin** — `wss://…трюкло…`
     **без** `/bridge/v2`: хвост приложение дописывает само (грабля 2026-10-14).
3. Привязка сохраняется между запусками, заново её делать не нужно, пока не сменился
   сервер. Mini App открывается кнопкой меню в чате бота или `https://t.me/<бот>?startapp`.

Что проверять дальше (не проверено живьём): остановка задачи с телефона, занятая беседа
и очередь, поведение при выключенном ПК, восстановление после обрыва связи.

Следующий этап разработки — **4. Устойчивость и уведомления**: reconnect/resync под
реальными обрывами, офлайн-состояния, несколько установок и уведомления через Bot API
(задача завершена, Кузьмич отключился, требуется действие на компьютере). Промты
исполнителям выдаются по той же схеме: Агент А — bridge и контракт, Агент В — relay
и Mini App.

Нерешённое организационное: хостинг, бюджет и ответственный за постоянный сервер;
судьба старого личного бота (выключен владельцем, код удаляется на этапе 5).
