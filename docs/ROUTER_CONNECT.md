# Подключение Codex к роутеру через портал

Спецификация импортирована 2026-09-25 из `codex-desk-connect.md`. После уточнения пользователя реализован основной сценарий: «Подключить через браузер» → подтверждение кода на портале → получение provider/defaults → предпросмотр → «Применить настройки». Скачивать и выбирать TOML не требуется. Проверки API выполнены на подставных ответах; реальный вход пользователя в SSO остаётся ручным.

Первоначально исследование web-интерфейса было ошибочно принято за доказательство отсутствия внешнего API. Наличие старого скачивания `/api/config/codex` не опровергает device endpoints для настольного клиента. Раннее изменение одной кнопки не выполняло задачу пользователя; ниже сохранены обнаруженный старый путь и исходный контракт.

Портал: `https://coder-portal.encycam.com`

Проверка доступности 2026-09-25: GET `/api/device/codex` → `405`, GET `/api/codex/provider` и `/api/codex/defaults` → `401` без авторизации. Это подтверждает наличие маршрутов; выдача личного ключа и настоящее SSO автоматически не проверялись.

## Что подтверждено на опубликованном портале

В публичном клиенте портала карточка Codex вызывает `GET /api/config/codex?scope=local|global` с browser-cookie и заголовком `X-Requested-With: fetch`. Ответ содержит `filename`, `path`, `config_text` и список `mcp_servers`; интерфейс портала создаёт из `config_text` скачиваемый TOML-файл. Без SSO-cookie этот запрос отвечает `401`. Сам портал предупреждает, что скачанный TOML содержит персональный router key и его нельзя коммитить, пересылать или публиковать.

Резервный путь в Desk: открыть `https://coder-portal.encycam.com/#codex`, войти в браузере, скачать файл, выбрать его в мастере и явно подтвердить полную замену. Desk не получает browser-cookie.

В опубликованном bundle найдены отдельные `/api/connect/codex` и `/api/connect/codex/status`, а административный device-поток находится под `/api/admin/pool/<subscriptionId>/device/*`. Это другие сценарии; настольный клиент использует переданные пользователем endpoints ниже. Отсутствие их вызовов в web-bundle не доказывает, что сервер их не поддерживает.

## Device flow

Заявка создаётся без авторизации:

```http
POST /api/device/codex
Content-Type: application/json
```

```json
{"client":"Codex Desk","host":"<имя компьютера>"}
```

Ожидаемый ответ содержит `device_code`, `user_code`, `verification_uri`, `verification_uri_complete`, `expires_in` (600 секунд) и `interval` (5 секунд). `device_code` — секрет только для host-процесса; renderer, логи и диагностика его не получают.

Приложение открывает `verification_uri_complete`, показывает человеку `user_code` и опрашивает:

```http
POST /api/device/codex/token
Content-Type: application/json
```

```json
{"device_code":"…"}
```

Результаты опроса:

- `200 {"api_key":"sk-…","email":"…"}` — одноразовая выдача ключа;
- `400 authorization_pending` — продолжать ожидание;
- `400 slow_down` — увеличить интервал;
- `400 access_denied` — показать отказ и завершить поток;
- `400 expired_token` — начать новый поток.

Исходная инструкция предлагала Credential Manager/DPAPI, но одновременно требовала `experimental_bearer_token` в общем конфиге. Для согласованного минимального сценария отдельного хранилища Desk нет: до применения ключ только в памяти host, затем — в стандартном config.toml для совместимости с терминальным Codex. UI об этом сообщает. При `401` временный ключ удаляется из памяти, требуется повторное подключение; `403` означает отключённый доступ. Отмена, закрытие окна и истечение срока также очищают временные секреты. Ключ и device_code не передаются в renderer или журналы.

## API настроек

Все запросы после device flow используют `Authorization: Bearer <api_key>`.

`GET /api/codex/provider` возвращает имя провайдера, `base_url`, `wire_api` и `requires_openai_auth`. `GET /api/codex/defaults` возвращает верхнеуровневые defaults: `model`, `model_provider`, `model_context_window`, `model_auto_compact_token_limit`, `model_reasoning_summary` и `hide_agent_reasoning`. `GET /api/codex/mcp` возвращает MCP-серверы пользователя, включая возможные личные токены в `http_headers`.

В реализации provider/defaults получаются только в host: фиксированный HTTPS origin, запрет redirect/cookie, таймаут 15 секунд и потоковый предел ответа 64 КиБ. Опрос соблюдает interval, slow_down добавляет 5 секунд; после одноразовой выдачи ключа сетевой сбой повторяет только GET настроек. MCP endpoint оставлен в спецификации для будущего расширения и сейчас не вызывается; существующие MCP сохраняются.

## Изменение `config.toml`

Целевой файл — `%USERPROFILE%\\.codex\\config.toml`, либо `<CODEX_HOME>\\config.toml` при абсолютном `CODEX_HOME`. Предложенный поток должен менять только поля, полученные от API, сохраняя собственные провайдеры, профили, проекты, MCP и историю пользователя. Перед записью нужны preview, резервная копия, проверка внешнего изменения и атомарный commit; существующие правила [настройки мастера](SETUP.md) и [MCP](MCP.md) остаются обязательными.

Фраза исходной спецификации «файл с ключом на диске больше не появляется» не относится к итоговому config.toml: `experimental_bearer_token` там хранится открытым текстом. Исключён промежуточный скачанный файл. Пользователь подтвердил реализацию этого сценария после объяснения записи ключа; резервные копии конфига также могут содержать секреты, как при прежнем ручном импорте.

Автоматическая синхронизация при запуске и отдельное обновление по сохранённому ключу остаются возможным расширением. Сейчас подключение запускается только кнопкой пользователя; настройки не меняются скрыто при запуске приложения.

## Реализация и ограничения

`router-portal.mjs` получает код и настройки. `portal-setup.mjs` принадлежит одному окну: scoped IPC принимает только flowId/previewId; чужое окно не может применить предпросмотр. `portal-config.mjs` читает единственный доступный базовый user-layer через `config/read`, сохраняет точные исходные bytes в backup и пишет отдельные поля через `config/batchWrite` с `expectedVersion` и `reloadUserConfig:false`. Сохраняются комментарии, profiles/projects, сторонние providers, MCP и `model_reasoning_effort`. Конфликтующая авторизация только выбранного provider очищается с указанием в preview. Другая запись после preview или во время backup отклоняется.

Шесть defaults из API и выбранный provider меняются после «Применить настройки». Запись резервируется общим SetupService: активные задачи/терминалы/подтверждения Codex должны закончиться; после сохранения idle-вкладки переподключаются. Модельные запросы и MCP tools не выполняются. Предпросмотр одноразовый, срок 10 минут. При отмене или закрытии окна отдельный служебный App Server останавливается.

Проверки: `tests/router-portal.test.mjs`, `tests/portal-config.test.mjs`, `tests/portal-setup.test.mjs`, preload tests, `test:setup`; `test:portal-host` использует настоящий Electron/IPC/установленный Codex в отдельном CODEX_HOME с fake HTTPS-ответами портала. Проверяются путь без скачивания, отсутствие записи до Apply, сохранность комментариев/effort/profiles/MCP, backup и конфликт внешней правки. Реальное SSO и личный ключ тестами не используются.
